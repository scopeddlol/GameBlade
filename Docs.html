GameBlade 0.6.1 GitHub API reference

    GameBlade

    A self-hosted platform for preserving free-to-play and DRM-free games: purpose-built Coordinator, Node and all-in-one Docker services, plus a Windows desktop client that makes playing from them feel like a modern game launcher.

    This page is the whole manual. The README is deliberately short — it exists to get a server running and to point here. Everything below is one file with no build step: open it in a browser to read it, open it in an editor to change it.

    Service, not just a web app

    AIO hosts files directly; a Coordinator connects storage Nodes. Both provide the landing page and admin panel, while playing happens in the desktop client.

    Read-only by design

    Your library is mounted :ro. GameBlade indexes and serves it; it never writes to it.

    Invite-only

    Self-registration is off by default. Accounts come from invite codes an administrator generates.

    Deploy it your way

    Use AIO on one host, or split the control plane from one or more storage Nodes.

    0.6.1 at a glance. The networking release is now separated into real products:

    • Three independent Docker images: Coordinator, Node and AIO.
    • A Node management UI with multiple libraries and selective or all-library scans.
    • Multiple Coordinator connections per Node, each with isolated enrollment state.
    • Automatic chunk hashing, one supervised serving agent per Coordinator/library pairing.
    • Bundled Caddy with automatic HTTPS in the Coordinator image.

    How the pieces fit

    Piece Who uses it What it does
    AIO (Docker) You The original single-container GameBlade experience, with optional P2P
    Coordinator (Docker) Administrator Admin UI, landing page, API, Discord bot, Caddy and mesh coordination
    Node (Docker) Storage operator Manages libraries, scans files and serves verified chunks to clients
    Landing page (/) Everyone Explains the archive and links the Windows client download

    There is deliberately no web library browser — that lives entirely in the desktop client. A player who signs in on the web lands on an account page (username, email, password, signed-in devices) instead.

    Where to get it

    Both halves are published together by CI — an image without a matching client leaves you nothing to connect with.

    Docker images ghcr.io/scopeddlol/gameblade-aio, ghcr.io/scopeddlol/gameblade-coordinator, and ghcr.io/scopeddlol/gameblade-node — latest, plus a tag per release.
    Windows client The .exe on the latest release. An .msi is there too for deployment tooling.

    Getting it running

    git clone https://github.com/scopeddlol/GameBlade.git
cd GameBlade
cp .env.example .env

    This quick start is for AIO. Edit .env, set LIBRARY_PATH, then:

    docker compose up -d

    Open http://<host>:8080 and create the first administrator account. That first-run screen is only available while the database has no users.

    Once the library has scanned, upload a client build from Admin → Settings (or point CLIENT_DOWNLOAD_URL at one hosted elsewhere) and invite people from Admin → Players → Invites.

    If it fails to start with a database error, the data folder is almost certainly owned by root while the container runs as uid 1000. SQLite is built into the image — nothing to install — it just cannot create its file: 

    sudo chown -R 1000:1000 ./data

    Alternatively set user: "1000:1000" on the service to match your own id -u/id -g.

    What a library looks like

    Anything at the top level of a library root is treated as one game — either a directory or an archive. Nested folders are indexed as that game's files, not as separate games. 

    /mnt/games/
├── Hollow Knight/            <- folder game
│   ├── hollow_knight.exe
│   └── data/
├── Stardew_Valley_v1.6.8/    <- folder game; version stripped from the title
│   └── Stardew Valley.exe
└── Celeste v1.4.0.0.zip      <- archive game

    Titles are cleaned before metadata lookup: version markers (v1.6.8, Build 12345), bracketed tags ([GOG], (2015)) and release-group noise (Repack, FitGirl) are removed. Dotted acronyms such as S.T.A.L.K.E.R. survive intact. Anything matched wrongly can be corrected by hand from the game's page.

    Running behind a reverse proxy

    The Coordinator image ships with Caddy. Set CADDY_ADDRESS=games.example.com, point that name at the VPS, and publish host TCP 80/443 to container 8080/8443. Caddy obtains and renews certificates and proxies to GameBlade on private port 3000. Use CADDY_ADDRESS=:8080 for HTTP-only LAN testing. If an external proxy already owns TLS, set CADDY_ENABLED=false, publish container port 3000, and route that proxy directly to it.

    Required in every case

    Set TRUST_PROXY=true. Without it every request appears to come from the proxy, which breaks per-client rate limiting and logs the wrong address.

    SECURE_COOKIES=auto (the default) marks session cookies Secure when the proxy reports X-Forwarded-Proto: https.

    On its own hostname

    Nothing else to configure. Point the proxy at http://gameblade:8080 and leave BASE_PATH empty.

    Under a sub-path

    Set BASE_PATH=/gameblade. The web client ships relative asset URLs and reads its own base path from a <base href> tag the server rewrites per request, so the same image works at / and at any sub-path with no rebuild.

    Do not strip the prefix at the proxy — GameBlade expects the full path.

    Pangolin

    Pangolin tunnels traffic over WireGuard and terminates it in Traefik, so the container needs no published ports at all. Remove the ports: block from docker-compose.yml and point the Pangolin resource at gameblade:8080 on the shared Docker network.

    Two things matter for large downloads through a tunnel:

    • Do not enable response buffering or compression. Game data is already compressed, so buffering only adds latency and memory pressure. GameBlade sets Cache-Control: no-transform and X-Accel-Buffering: no on download responses to say so explicitly.
    • Allow long-lived responses. A multi-gigabyte transfer can run for hours. GameBlade itself applies no request timeout; make sure the proxy doesn't either.

    Tunnel throughput is the usual bottleneck on a large download. That is precisely what the desktop client's downloader is for.

    Three services, three images

    v0.6.1 gives each deployment shape its own artifact. Matching version tags keep the wire protocol aligned, while separate images prevent a Coordinator from accidentally running a scanner or a Node from exposing the full admin and player API.

    RoleHoldsRuns where
    gameblade-aio Everything: database, panel, and the games on local disk One machine. The default, and what GameBlade has always been.
    gameblade-coordinator Database, admin panel, landing page, API. No game files. A VPS. Small, because coordination is kilobytes.
    gameblade-node One or more game libraries, a management UI, scanner and serving agents. Wherever the library lives.

    Pin the same release tag. Upgrade Coordinator, Nodes and desktop clients together. AIO remains the compatible path for existing single-host installations and still accepts the old ROLE=standalone value.

    Node management, libraries and Coordinators

    1. Mount every host library read-only into the Node container.
    2. Open the Node UI (port 8081 in the example Compose file), create its administrator, and add each container path.
    3. Generate an Origin enrollment in a Coordinator, then add a connection in the Node UI and choose which library it publishes.
    4. Repeat for additional libraries or Coordinators. Every pairing has its own identity, token and serving process.
    5. Use Scan beside one library or Scan all. The Node computes verification chunks automatically before publishing.

    A library may be connected to several Coordinators, and one Node may serve unrelated libraries to different Coordinators. Additional agents use consecutive UDP ports beginning at MESH_PORT. The example Compose file publishes 47820-47839/udp for up to 20 pairings; outbound NAT discovery normally works without a forward, while forwarding the matching range improves direct LAN/WAN reachability.

    Moving an existing install to a coordinator

    This is a copy, not a migration. The database is not converted or restructured; it is the same file, opened by the same code, on a different machine.

    1. Back up first. Admin → Insights → Health writes an archive of everything that cannot be recreated. Copy it somewhere that is not the machine you are moving off.
    2. Copy data/ to the new host. Copy, never move — the original stays where it is and stays whole.
    3. Start gameblade-coordinator and check it while the old instance is still the live one: sign in, browse the catalog, open a save, read a message.
    4. Enrol gameblade-node for the library that holds the games. Existing migrated catalogs should be assigned to their existing logical library; a new Origin creates its logical library automatically on first report.
    5. Point the proxy at the coordinator only once all of that looks right. If anything is wrong, point it back — the old instance is untouched.

    Assign the right library when migrating. A node's catalog is matched into a library by relative path, so reporting into the library those games are already in updates those entries and every game keeps its id — and with it every achievement, save rule, artwork match, favourite and playtime record. Pointing a node at a different library would add the whole catalog again as new games and leave all of that attached to entries nothing references. Fresh Origin enrollments create a logical library automatically; mirrors and migrated catalogs should be assigned explicitly.

    The relay

    A coordinator holds no game files, so there is no plain HTTP download to fall back to when a client cannot reach a node directly. The relay is that fallback. Both ends dial out to it — which always works, because it has a public address — and it pastes the two connections together.

    It is the least clever component here on purpose. It never terminates TLS, never parses a chunk request, never learns which game is moving through it, and holds nothing but a table of which two sockets belong together. The QUIC session runs end to end between the client and the node, so what passes through is ciphertext it could not read if it wanted to — and every guarantee made elsewhere survives untouched: the client still pins the node's identity, the node still checks the grant, the client still verifies every chunk against its hash.

    It needs the coordinator's public key and nothing else. No database, no credentials, no API. In v0.6.1 the Coordinator supervises this relay itself whenever RELAY_ENDPOINT is set.

    It is not faster. It is strictly slower than a direct connection — an extra hop, over this host's pipe. It exists so those downloads happen at all. Only clients that failed to connect directly ever use it, relayed bytes count against the same allowance as any others, and GAMEBLADE_RELAY_MAX caps how many can be in flight so the exception path cannot quietly become the main road.

    Leaving RELAY_ENDPOINT unset means there is no relay, and a client that cannot reach a node directly cannot download from it. Run mesh-doctor on the node first: if it reports the connection punchable, most clients will reach it without the relay ever being asked.

    The mesh: downloading without the tunnel

    Every byte of every download crosses the proxy, because the proxy is the only thing on the public internet. On a VPS with modest bandwidth that is the ceiling on how fast anyone can install anything. The mesh removes it: a client connects straight to a machine holding the files, and the server keeps doing the part that is actually small — saying who is out there and granting permission.

    It is not a VPN, and nothing is installed. A VPN would mean a virtual network adapter, which on Windows means a driver, an elevation prompt, antivirus attention and a firewall dialog — all so the operating system can route packets that only ever reach one process. The client speaks QUIC directly instead, terminated inside the app. There is nothing for a player to install, approve or notice.

    What a node is

    A Node is the storage service: it can mount several libraries and connect each one to one or more Coordinators. Every connection is known by its own Ed25519 key rather than its address, because a machine on a home connection gets a new address whenever the lease renews.

    Nothing a node says is trusted. Its claim to hold a game is a hint about who to ask, not a promise; every chunk is verified against a hash this server computed, on the node before it sends and on the client before it is used. A node can be stale, wrong, offline or hostile and the worst outcome is a slower download. That is what makes enrolling one an operational decision rather than a security one.

    Turning it on

    1. Add and scan the libraries in the Node UI. A game is only eligible once every file has per-chunk hashes. The Node now computes them automatically after a scan; use one library's Scan button or Scan all.
    2. Enrol the node. Admin → Settings → Nodes generates a one-time code. It is shown once and stored only as a hash; it expires in 24 hours and is spent the moment a node registers with it.
    3. Add the connection in the Node UI, choose its library, and paste the code. The image supervises the serving agent; there is no second container to start.
    4. Switch the mesh on in Admin → Settings → Bandwidth. Until this is on, nodes may register and sync but no client is ever pointed at one — so a node can be enrolled and left to fill up first, and turning it on is a switch rather than a migration.

    Forward the Node's UDP range when practical. The first connection uses MESH_PORT (47820 by default) and additional connections use consecutive ports. This is the single cheapest thing you can do for reliability. Two machines both behind NAT have to punch a hole through it, which usually works and sometimes cannot — a symmetric NAT or a carrier-grade one defeats it. If one side is directly reachable, the problem essentially disappears regardless of what the other side is behind. Without a forwarded port, expect some players to quietly fall back to downloading through the proxy.

    What the server still does

    Coordination is kilobytes — keys, addresses, counters — which is why it fits on a small VPS. No game data is ever stored here for the mesh.

    Transfer allowances survive the change. A client is issued a signed grant carrying a byte ceiling, the node enforces it locally and reports back what it served, and those bytes count against the same monthly quota as anything downloaded from this server. A node that stops reporting is a node whose grants stop being renewed.

    A mirror announces the fingerprint of the copy it verified. When a game changes on the origin the fingerprint changes with it, and mirrors still announcing the old one stop being offered — no diffing, and no relying on a mirror to notice.

    Letting players share

    Let players share what they have downloaded is a separate switch, also off by default, and deliberately not implied by the one above. The first shares machines you run; this one turns players into distributors of each other's downloads, using their upload bandwidth. Each player must also opt in on their own client, and neither switch turns the other on.

    A sharing client serves only games it has fully installed, only to accounts holding a valid grant, and never to its owner. Every piece is re-checked against the manifest before it is sent, so an edited or modded install simply stops being a source. Turning the server switch off stops every sharing client within one heartbeat, without having to reach any of them.

    When it does not apply

    In AIO mode, mesh failures fall back to the local HTTP origin. A split Coordinator has no game bytes, so it never advertises that nonexistent origin: clients use a direct Node or the encrypted relay. An older client that does not understand this split should be upgraded alongside the Coordinator and Nodes.

    Metadata providers

    Both are optional — GameBlade runs fine without them, it just shows titles and file sizes instead of artwork. Add credentials in Admin → Settings, or via environment variables.

    ProviderWhat it suppliesCredentials
    IGDB Summaries, release dates, genres, ratings Create an app at dev.twitch.tv — IGDB uses Twitch OAuth
    SteamGridDB Posters, capsules, hero art, logos, icons Your SteamGridDB API preferences

    IGDB enforces 4 requests/second; GameBlade rate-limits itself to stay under that, so a first scan of a large library takes a while but never gets throttled out. Artwork is downloaded once and cached locally, so the library keeps rendering if a provider is unreachable — and no client IP is ever exposed to a provider.

    The admin panel

    Everything an operator needs, at /admin — and it works on a phone: below the large breakpoint the sidebar becomes a drawer, and tables and charts stay inside the viewport rather than forcing the page sideways.

    Six sections, each with its own sub-tabs. Pointing at one starts fetching what it needs before the click lands, and a page waiting on data draws its own shape rather than a spinner. The flat URLs the sections used to live at still work and redirect.

    Overview

    Catalog health, connected clients, scan progress, and a broadcast announcement box that pushes a notification to every account.

    Catalog

    • Games — a worklist of every game, filterable by match status and by what an entry is still missing: no launch executable, no cloud-save rule, no artwork, no achievements, no metadata. Each filter carries a server-wide count, and every row shows the same four things as EXE / SAVE / ART / ACH markers, so a scan down the list says where the holes are without opening anything. Opening one gives a full metadata editor: fields, artwork slots, screenshots, Steam achievement import, and the launch and save rules the desktop client needs.
    • Achievements — the same job across the whole catalog rather than one game at a time. See In bulk.
    • Featured — curates the carousel on the client's Home tab, in order, with a per-slot image override.
    • Save paths — where each game keeps its saves. See Where the save paths come from.
    • Libraries — the folders on disk that are scanned, and the scan itself. See Scanning.

    Players

    • Accounts — who is here, and their roles.
    • Invites — codes, their uses and their expiry.
    • Game requests — the queue, ranked by how many people asked. See Game requests.
    • Bug reports — the triage queue. See Reporting a bug.

    Insights

    • Analytics — who downloaded what, the most-played titles, bandwidth per day and per month, allowance usage, and a recent-downloads log. Everything is derived from the download and play records already being written, so there is no separate counter to drift out of agreement with them.
    • Health — what needs attention, the backup schedule, and database maintenance.

    Appearance

    • Theme — the colour preset and accent, applied to the panel around you as you pick, and put back if you leave without saving.
    • Landing page — the public page as an ordered list of sections, with a live preview. See Editing the landing page.
    • Desktop client — your own links (a Discord invite, a wiki, a support page) rendered in the client's sidebar, on its Home tab, or in the right-click menu. Links only: the client hands the URL to the player's browser, and only http(s) is accepted — pushing anything executable to every player's machine would be a different trust model entirely.

    Settings

    • Server — the name and tagline, provider credentials, the Windows client installer, and the bandwidth limits.
    • API keys — scoped credentials for the external API.

    Scanning

    A scan walks each library root, reconciles what is on disk against the catalog, and then asks the metadata providers about anything new. Admin → Catalog → Libraries starts one and shows what it is doing.

    The scanner was rebuilt in 0.5.3. If you have been living with a scan that ran from boot and never finished, this section is the one to read.

    The three phases, and what their numbers mean

    PhaseThe count is
    Reading Top-level folders inspected, out of how many the root holds. It cannot know how many games that will be until it has looked inside each one.
    Indexing Entries reconciled with the database, out of what reading found.
    Fetching metadata Titles asked about, out of everything still waiting on a provider.

    Counters are cleared when the phase or the library changes. They used to carry over, which is why a run part-way through its second root would sit on the first root's finished tally — a complete-looking number that was not measuring anything.

    Skip, Stop, and the stall warning

    Skip this one abandons whatever is in front of the run — an unreadable folder, a provider that will not answer — and moves on. It aborts the request in flight rather than waiting for it, so it takes effect immediately.

    Stop the scan ends the run at the next checkpoint. What has already been indexed stays indexed; a cancelled scan is a partial scan, and the next one carries on from there.

    If no counter has moved for three quarters of a minute, the panel says so and how long it has been. A working scan and a wedged one look identical from a progress bar; that line is the difference between waiting sensibly and waiting for ever.

    The ceilings

    Every phase carries a deadline, because each of these has caused a run to hang:

    • 90 seconds per title during metadata. A title is not one request — it is a search, a fetch, a cover and up to twelve screenshots, each with its own timeout and retry. Multiplied out, one game could legitimately occupy a run for the better part of an hour.
    • 30 minutes per library during reading. A share that has gone away does not fail, it hangs: every directory read blocks on a mount that will never answer.
    • Twelve screenshots per game. Nobody scrolls to the thirtieth, and each one past that is a download the first scan of a library pays for, per game.

    The reading walk hands the event loop back every two hundred entries, so the server goes on answering requests — including the progress endpoint you are refreshing to find out what is happening — while a large share is being read off a slow disk.

    What enrichment does and does not touch

    Enrichment is a first-time job. Once a provider has written to a game, it is left alone, so a title corrected by hand or artwork chosen deliberately survives the next scan. Clearing a match from the game's page is what puts it back in the queue.

    A game the providers have never heard of is set aside for the rest of the pass rather than re-asked in every batch, and the run says at the end how many are still without metadata so they can be matched by hand.

    A game that vanishes from disk is flagged, never deleted — an unmounted share must not destroy hand-made metadata matches. Remove missing on the catalog page clears the flagged ones out when you actually mean it.

    The database

    SQLite, in DATA_DIR, with plain-SQL migrations applied at boot. There is nothing to administer day to day — but a catalog on a spinning disk is a different proposition from one on an SSD, and 0.5.3 tunes for it.

    A 64 MiB page cache, a memory map, 8 KiB pages on a newly created database, and a write-ahead log that checkpoints a quarter as often. Ten indexes were added for queries that had none: every shelf and library page filters on "not missing" and then sorts, which a single-column index only half satisfies.

    Maintenance

    Statistics and a log checkpoint run hourly by themselves. SQLite only gathers query statistics when asked, so a catalog that grew from fifty games to five thousand is otherwise still being planned as though it were small — and on a disk that charges milliseconds per seek, a plan that scans instead of seeking is the difference between a page load and a wait.

    Admin → Insights → Health → Database has both jobs as buttons:

    • Refresh statistics — cheap, safe at any time. Worth pressing right after importing a large library rather than waiting an hour for the hourly run.
    • Rebuild and compact — rewrites the file with its pages in order and gives back unused space. This is the one that repays real time on a spinning disk, and also the expensive one: it needs room for a second copy of the database on the same disk and holds a write lock for as long as it takes. The panel shows how much there is to reclaim so you can judge whether it is worth it.

    Users and invites

    Registration is invite-only unless an administrator turns on self-registration in Admin → Settings.

    To add someone: Admin → Players → Invites → Create an invite, then send them the copied link. Invites carry a role, a use count and an optional expiry, and can be revoked at any time. After registering they download the Windows client and sign in there — the web surface has nothing else for them.

    Changing a password signs out every other session and revokes every desktop device for that account.

    Working on the catalog

    Picking artwork

    Every image slot — cover, banner, hero, logo/text, icon, and each screenshot — has a Browse gallery button that opens a picker over everything IGDB and SteamGridDB publish for that title. Search by whatever the providers call the game rather than what the folder is called, and narrow by SteamGridDB style (a white or black text wordmark, a capsule with no logo baked in, and so on). The screenshot picker stays open so a set can be assembled in one pass.

    Previews are streamed through the server rather than loaded from the provider CDNs, so a browser never talks to IGDB or SteamGridDB directly. Only the image actually chosen is downloaded and cached.

    Launch and save rules

    These are what turn an archived folder into something playable:

    • A launch rule names the executable relative to the install folder. Leave it blank and the client picks the largest .exe that is not obviously an installer or uninstaller.
    • A save rule says where the game keeps its saves, using placeholders that resolve on each machine: {userprofile}, {appdata}, {localappdata}, {documents}, {savedgames}, {public}, {programdata}, {windir} and {install}. Optional include and exclude globs narrow it further.

    Checksums

    Compute checksums on a game hashes every file so the client can verify what it downloads. It is opt-in per game because hashing reads every byte and is far too expensive to do automatically across a multi-terabyte archive. Verify re-hashes what was hashed before and records whether each file still matches — for an archive, a changed file is almost always corruption rather than an edit, and nothing else here would ever notice.

    Games players already have

    A player with a drive full of games should not have to download a second copy of any of them. Library → Import points the client at a folder, finds every subfolder holding a Windows executable, and matches those names against the catalog — through the same title parser the scanner uses, so a Hollow.Knight.v1.5.78.11.GOG-FitGirl folder still resolves. Each row is confirmed by hand before anything is linked, because a wrong match would attach the wrong cloud saves to the wrong game.

    Linking copies and moves nothing; the files stay where they are. Unlinking is therefore a separate action from uninstalling, and only the latter deletes.

    Cloud saves

    The client hashes the save folder, zips it, and uploads it as an immutable version. Ten versions are kept per slot, so a bad sync is always recoverable.

    Conflicts are detected rather than guessed at. The client remembers the digest it last synced; when the cloud has moved on from that digest and the local copy has changed too, both sides hold edits and the client asks instead of picking a winner. Launching a game pulls a newer cloud save first, but deliberately does not resolve a conflict — starting a game is the wrong moment to make someone choose which save to destroy.

    Restoring moves the existing save folder aside rather than deleting it, so the previous state stays on disk even if the archive turns out to be wrong.

    Automatic syncing

    The setting has said "pull before launching and push after quitting" since the client was written, and only the pull was ever implemented — so a player who trusted it had a cloud copy frozen at whenever they last pressed Upload, and a fresh install would then restore that over their real progress. Uploading now happens too.

    Settings → Cloud saves in the client. The master switch turns automatic syncing on; underneath it, three controls decide when:

    • Upload when a game closes. On by default. There is a short pause first — a game writes its save on the way out and the process is gone before the disk has finished, and packing the instant the process disappears uploads the save from before the session.
    • Catch up on sign-in. On by default. A crash, a power cut or closing the launcher mid-game all end a session with nothing uploaded; this is the sweep that notices, and it is why "automatic" can be trusted at all.
    • Back up while playing. Off by default, five minutes to an hour. A long session that ends in a crash otherwise loses everything since it started. It costs an upload per interval, and for a game that holds its save file open it can capture a half-written one — hence off unless asked for.

    A conflict is never resolved automatically. That stays a decision on the game's page.

    Where the save paths come from

    Finding where a game saves by hand means installing it, playing it, making a save and going looking — for every title. Admin → Catalog → Save paths matches the catalog against Ludusavi's manifest, a machine-readable digest of PCGamingWiki's save-path data covering close to twenty thousand games, and proposes the rules instead.

    Nothing is written without a tick, and the manifest's own title is shown beside the archive's on every row, because a title match is occasionally confident and wrong — and these paths are where the client will later read and write a player's saves. Titles that already have a rule are hidden by default.

    The index refreshes itself daily, decided from its own age rather than run on a timer, so a server restarted every evening still refreshes once a day and one left up for months does not drift. Refresh index forces it.

    Achievements without cloud saves

    A game with unlock rules and no save rule is not a game whose save location is unknown. An unlock rule reads a file the game wrote into its own save folder — a Goldberg achievements.json, an emulator's progress log, a stats file next to the slots. So the location has already been written down, in a column that syncs nothing.

    The same page now derives them. Rules pointing into one folder fold into a single proposal; a nested path folds into its parent; two genuinely separate layouts — a retail install and an emulator — are offered as a choice rather than one picked at random. Nothing is written without a tick, and a game that has gained a rule since the page loaded is left alone.

    Health calls this out separately from the plain "no save rule" count, because those players lose their unlocks along with their saves the first time they change machine — and a save can be copied back by hand, while an unlock cannot.

    Achievements

    Games here have no achievement runtime of their own, so definitions are imported and unlocks are reported by the client.

    Import a set from Admin → Catalog → Games → (a game) → Achievements with a Steam app id. This reads Steam's published achievement schema — no player data is requested and no Steam account is linked — which is what makes it usable for a DRM-free copy of a game that also ships there. Global unlock rates come along with it and set each achievement's point value.

    In bulk

    One game at a time is right for a correction and hopeless as a way to cover a catalog of several hundred, so Admin → Catalog → Achievements does the same job across as many games as you select.

    It starts on the games that have none. Tick the ones you want — or all of them — and it works through the list, finding each on Steam, importing its published list and writing the unlock rules, a few games at a time so you can watch it go and stop it. Every game gets a line saying what happened, and the ones that could not be done automatically sort to the top: a title Steam places ambiguously, one it has never heard of, and one whose store entry has no achievements are all ordinary across a real catalog, and each is a note rather than a failed run. Games that already have achievements are left alone unless you say otherwise.

    For the games Steam cannot help with — a fan translation, an itch-only release, a version whose store entry predates its achievements — the same page takes a pasted list. One per line: the name, then optionally a description, a point value and a key, separated by tabs, commas or pipes, so a column copied out of a spreadsheet or a wiki table works as it is. A missing key is derived from the name and stays stable, so a corrected list can simply be pasted again.

    Achievements that unlock themselves

    Definitions have always been importable; a rule is what says when one is earned. It names a file the game itself writes and what to find in it — a JSON path, an INI key, or a regular expression over text — tested for presence, truthiness, equality, or a threshold.

    The client reads those files when a session ends and reports only the resulting keys; the files never leave the machine. A reported key with no rule behind it is ignored, so reporting is not a way of simply asking for an achievement, and unlocking is idempotent, so re-reading the same save changes nothing.

    One achievement often needs a rule per save layout it might turn up in — Goldberg, a retail install, an emulator — all naming the same key and told apart only by a long path. Rules carry operator tags for exactly that, on the rule rather than on the achievement, because the rule is the only thing that distinguishes them.

    Because the client is the only thing that can observe progress, unlocks are self-reported and therefore not cheat-proof. The server keeps them idempotent and well-formed; it does not adjudicate them.

    Game requests

    Players ask for what is not there, and the archive keeps a queue of it.

    The client's Requests tab is where players ask and vote: a tally of what is open, on the way and already added, a search, filters by state, and the queue ranked by votes. Two people asking for the same game strengthen one row rather than producing two the operator has to reconcile — titles are matched on a normalised key, so Half-Life 2: Episode One and half life 2 episode one collide, while Halo and Halo Wars stay apart. The asker's vote is counted automatically, and anyone else can back a row or take their backing away.

    Above the queue sit discovery shelves: what is being played elsewhere, what is anticipated, what is newly out and what is best reviewed, from IGDB. Each card is checked against this archive first, so its button reads In the archive, Backed, Back it or Request — one click, no typing. It needs IGDB credentials; without them the shelves simply do not appear and the rest of the page works as normal. The lists are cached for an hour, since they are the same for every player and IGDB's rate limit is shared with scanning and matching.

    Cards are clickable. A title the archive already has opens the game — the same panel the Store opens, with its screenshots, its size and its Install button. One it does not have opens what the provider told us about it: the cover, the full blurb, the year, the score, and the button that asks for it. That is deliberately not the game drawer, which is built around a game that exists here; reusing it would have meant a page of dead Install and Play buttons.

    Admin → Players → Game requests is the other side of it: the queue ranked by votes, with four states — pending, coming soon, added, denied — a note players will see, and a field linking a fulfilled request to the catalog entry that satisfied it. Who asked is shown here and nowhere else; a wish list should not become a public record of who wants what.

    The client's Home tab draws the result: Coming soon for what has been promised, Most requested for what is still wanted, and Recently granted for requests that made it in — with an Open button straight to the game. A denied title reopens as pending if somebody else asks for it, because the second asker never saw that decision.

    Social, news and profiles

    The feed

    Screenshots, clips and text, with comments and reactions. Friends have live presence and a shared activity feed. Clips play where they sit with the browser's own controls, and expand into the media viewer from a corner button.

    News and announcements

    The broadcast box on Admin → Overview, or the composer on the client's News tab, sends a notification to every account and publishes the same text as a post. The notification is read once and gone; the News tab is where it stays, and where people reply to it. Underneath it is an ordinary post, so comments, reactions, editing and deletion are the machinery the social feed already had.

    Two announcements are deliberately not published: one aimed at named accounts, which is a message rather than a notice, and one an operator marks as transient ("back up in five minutes"). Players cannot author one — the post route derives its kind from what was attached, so asking for kind: announcement in a request body is ignored rather than trusted.

    Profiles

    A display name, a bio, an avatar, a banner, an accent colour, a country, and who may see any of it — everyone on the server, friends only, or nobody. A private profile still resolves so the "add friend" screen has a name to show, but every statistic is withheld rather than faked.

    0.5.3 adds room for a profile to be somebody's rather than a name and an avatar:

    • Pronouns. Free text rather than a list of options, because no fixed list is complete and one that is not gets it wrong for exactly the people it matters most to. Shown beside the name, and visible even on a private profile — withholding it would make a locked-down profile misgender its owner to everyone who visits.
    • A status line, distinct from the bio: what, right now.
    • Banner framing. A banner is a wide crop of a much taller picture, and left at dead centre it beheads people. A slider chooses which band survives.
    • Up to five labelled links. Capped, because an uncapped list becomes a link farm; labelled, because an unlabelled URL on somebody's profile is one nobody clicks. Only http(s) is accepted, checked on both sides.
    • One pinned game, as distinct from "most played" — which is what the section calling itself Favorite games actually was, and is now labelled as.

    Showing a Discord handle

    A linked player's handle is private by default. The toggle lives on their account page, and re-linking — which happens on every Discord sign-in — does not turn it back on.

    Turning it on used to change the friends rail and nothing else, including the profile page it is named after. Every path that builds a profile summary now resolves the handle the same way, so the answer is the same everywhere.

    Messages

    The Messages tab in the client. Text, images and video, between friends or in a group of up to 32.

    Using it

    • Friends only. An archive with open messaging is one where any account can send anything to any other, which is the shape every spam and harassment problem takes. Adding somebody is already the gesture that says "I want to hear from you".
    • Picking more than one person makes a group. Whoever starts it owns it and can rename it and add people; anyone can leave. A member who leaves stays in the record with a departure date, so the messages they sent still have a name against them.
    • Attachments are ordinary uploads that count against the same media quota as screenshots and clips, and open in the media viewer.
    • Withdrawing a message clears its text rather than hiding the row, so every client agrees it is gone. It does not reach into the screen of somebody who has already read it, and nothing could.
    • Enter sends, shift+enter breaks the line. The composer is pinned to the bottom of the window and the conversation list scrolls beside it, so neither moves with however much history is above them.

    These are not end-to-end encrypted, and the operator can read them. 0.5.3 shipped an encrypted version and 0.5.3 took it back out: the cost was out of proportion to what this is. An operator already holds every save file, every screenshot and every password hash on the server, so wrapping message bodies protected nothing that was not already readable — while adding a failure mode that was very real, where a device with no key wrap for a conversation could not read a word of it and nothing could recover one.

    Access control is the security model, and it is the half that was always doing the work: friends only, membership checked on every read and write, and an attachment that has to belong to whoever is attaching it. Treat a conversation as private from other players and visible to whoever runs the server — which is the same understanding that already applies to everything else stored here.

    The desktop client

    The client is where players spend all their time.

    TabWhat is there
    HomeYour own totals, an auto-advancing featured carousel, jump back in, friends playing, what is coming soon and most requested, activity, recent unlocks
    LibraryGames you own, as posters or as a dense list — install, launch, playtime, achievements, save sync and your own groups
    StoreThe whole archive, filterable, one click to add to your library
    RequestsAsk for what is missing, and back what others asked for
    NewsAnnouncements, and the replies to them
    SocialFeed with screenshots and clips, comments, reactions, friends and requests
    MessagesConversations with friends and groups
    SettingsProfile, appearance, install locations, save sync, presence, devices, your bug reports

    Adding a game to your library applies immediately and only to the card you clicked, so a run down the store adding a dozen titles is a dozen clicks rather than a dozen round trips waited out one at a time.

    Installing, launching and playtime tracking are handled in Rust: the client extracts the archive, resolves the executable, watches the game process and banks playtime as it goes, so a crash mid-session still keeps most of it.

    Presence, friend activity, notifications and new messages arrive over a WebSocket that reconnects with backoff. Everything it carries is also readable over REST, so a dropped socket costs freshness, never correctness.

    Stopping a game

    While a game runs, the Play button used to become a greyed-out "Running" — true, and no help at all to somebody whose game has hung behind a fullscreen window they cannot get back to. The only way out was Task Manager.

    The game's page, the right-click menu and the chip in the title bar all offer Stop. The process is asked to close first, so a game that handles the request gets to save, and killed five seconds later if it does not answer. Playtime is recorded exactly as for a normal exit, because it was time played.

    Library layouts

    LayoutFor
    GridBrowsing by artwork
    ListFinding a title you already know — four or five times as many rows on screen
    DetailedDeciding what to play: cover, blurb, genres and every stat spelled out

    Switched from the toolbar rather than from Settings, because which one is right changes with what you are doing. The choice lives in the client's settings file, so it survives a restart. Game pages show a title's logo artwork in place of its name wherever the archive has one; Settings → Appearance turns that off for anyone who would rather read the title.

    Groups

    A player's own shelves, private to their account. Right-click any game and choose Add to group… to file it — or make a group in the same dialog and file it there in one step. The Library tab then shows a chip per group beside the search box.

    Groups are per-account rather than server-wide: an operator already has genres and the featured rail to shape the catalog, and a shared group would need its own permissions model to answer "who may rename this". Nothing is copied or moved, and deleting a group leaves every game in it alone.

    The media viewer

    Screenshots used to open into the 440-pixel dialog the app uses for confirmation prompts, so a 1080p capture rendered at about a fifth of its size with text buttons underneath for Previous and Next. Trailers left the app for a browser.

    Both now open the same full-viewport viewer: arrow keys between items, a filmstrip, a counter, and a fit/full-size toggle for reading small text in a capture. Trailers play inline through YouTube's privacy-preserving embed host with related videos from other channels switched off, and "Open on YouTube" is still there. Clips in the feed and attachments in a conversation play with the browser's own controls — scrubbing, volume, playback rate, picture-in-picture.

    Working offline

    The archive runs on your own hardware, so it is down sometimes — a reboot, a moved cable, a laptop on a train. Any of those used to take the whole client with it: the sign-in check failed, the app fell back to the login screen, and the login screen could not reach the server either.

    What works with the server unreachable:

    • You stay signed in. An unreachable server is not the same answer as a revoked device, and is no longer treated as one.
    • Installed games launch, and playtime is recorded when the server comes back.
    • The library lists what is on this disk, from the install records themselves — so changing the sort does not empty the page.
    • Pages you have already visited render from the last answer the server gave.
    • Artwork falls back to the initials placeholder rather than a broken-image icon. Covers are fetched from the server, so offline the library is a grid of titles rather than posters — plainer, and a great deal better than no app at all.

    A banner says what still works rather than only that something is wrong. Anything that writes fails with "this needs a connection" instead of a TLS error. Messages are the one feature that genuinely cannot work offline, and the tab says so.

    Downloads

    Pressing Install asks where the game should go rather than silently using a default. Every configured drive is listed with what is free, what would be left after, and a plain refusal when the game will not fit — a download that dies at 90% for want of disk is the worst way to find that out. Add more locations under Settings → Storage.

    A browser download of a 60 GB folder is a single connection that has to survive from start to finish; if it drops at 90%, it starts over. The desktop client exists to remove that failure mode.

    • Fetches a manifest of every file in a game with a short-lived signed token.
    • Multiple connections per file (files ≥ 32 MB are split into four ranges) and several files in parallel.
    • Resumes after a disconnect, a crash or a reboot. Progress is journalled to a .gbpart sidecar next to each file, so a transfer picks up at the exact byte it stopped.
    • Retries with backoff — a flaky tunnel recovers on its own instead of failing the download.
    • Verifies SHA-256 when the server has a checksum for a file. See Checksums.
    • Signs in with a device token in the Windows Credential Manager, never a password on disk. Each device is listed and revocable from Settings.

    Cancelling asks what to do with the bytes already on disk. Stopping a 250 GB install 100 GB in leaves 100 GB somewhere, and both answers are legitimate — a transfer stopped to be resumed later wants its files, one being abandoned wants the space back. Keeping them is the default; removing them deletes exactly the paths that download wrote and nothing else in the folder.

    Web downloads still work for everything: archive games stream with byte-range resume support, and folder games are packaged into a ZIP on the fly.

    Right-click menus

    Right-clicking a game anywhere in the client — Home, Library or Store — opens a menu with everything that applies to it: play, stop, install, add to library, favourite, open the install folder, unlink, uninstall, plus any custom buttons placed there. Text fields keep the native menu, so copy and paste still work.

    Keeping the client up to date

    Upload a new installer under Admin → Settings and bump the client version beside it. Clients older than that version show a banner offering to update, and hand off to the installer when the user accepts — nothing is replaced behind their back. Declining is remembered per version, so saying no to 0.5.2 stays no while 0.5.3 asks again. Nothing is offered unless an installer has actually been uploaded.

    Reporting a bug

    Report a problem sits in the client's sidebar, reachable from wherever something went wrong rather than on a page somebody has to go and find. The report carries the client version, the platform, the game if one was running, and the last few errors the app logged — none of which a reporter should have to know, and all of which an operator would otherwise have to go back and ask for.

    Admin → Players → Bug reports is the queue: filter by state, read what the app logged just before, and answer. Whatever you set, and anything you write back, reaches the reporter as a notification, and they can see where each of their reports got to under Settings.

    That last part is the point rather than a nicety. Somebody who reports a problem and never learns whether it was read, fixed, or was never a bug has no reason to report the next one, and an archive tested by the people using it depends on them doing so. Unanswered reports show up on the health page for the same reason.

    Discord

    Entirely optional — with none of it configured, GameBlade behaves exactly as it did before. Admin → Settings → Discord has two independent halves.

    Sign in with Discord

    Needs a Discord application's client ID and secret. Players can then link from their account page and use it to sign in. Linking never creates an account: this server is invite-only, so an unlinked Discord is told to sign in normally once and link. The redirect URI registered on the application must exactly match <your server>/api/auth/discord/callback.

    With a guild ID set, linking also checks membership of your Discord, and the bot adds them to it using the guilds.join scope they granted — being told to go and join is a step people do not take. If that fails, they get your invite link instead. Require players to be in the server refuses the link outright when neither works.

    Starting the bot

    A token lets this server post; it does not make the bot online. Being in the member list, answering a slash command and reacting to a button all need a live gateway connection, and Start the bot is what opens one. The switch is remembered, so the bot comes back by itself after a restart, and it reconnects on its own if Discord drops it. A wrong token stops it outright and says so rather than retrying for ever.

    Intents are assembled per feature, so a server using none of them keeps exactly the bot it had: Guild Members is added only when an auto-role is set, and Message Reactions only when reaction roles are switched on. Both are read at connect time, so changing either reconnects rather than leaving a live socket listening for events it never asked for. Guild Members is privileged and has to be enabled in the developer portal — the panel says so, because that is the step that otherwise fails as "the bot will not connect".

    How it appears sets the coloured dot (online, idle, do not disturb, invisible) and the line under the name: Playing, Streaming, Listening to, Watching, Custom or Competing in, plus the text. A change is pushed over the open connection, so it takes effect immediately rather than bouncing the bot offline and back.

    Posting, and tagging people in a post

    Post something goes to whichever channel you pick — the channel and role boxes are real pickers once the bot can see your server, and fall back to pasting an ID when it cannot. An attached image is sent as a genuine Discord attachment rather than as a link, so it works whether or not this server is reachable from the internet.

    The composer has three pickers — people, roles, channels — that insert a real mention at the cursor. Typing a snowflake by hand works and nobody does it: it has to be copied out of Discord with developer mode on, and a mistyped digit produces a post that looks fine and pings nobody.

    Discord never notifies for a mention inside an embed. A role pill in an embed description renders correctly and reaches nobody — that is Discord's rule, not a formatting mistake, and there is no flag that changes it.

    The only fix is to repeat the mentions in the message content that carries the embed, which the composer offers as Notify the people tagged and explains rather than leaving to be discovered. Untick it for a post that should mention somebody without pinging them.

    Every outgoing message carries an explicit permission list naming exactly the ids the text contains. Omitting that field would tell Discord to notify anything that looks like a mention, which is how a game summary containing the word @everyone would ping a whole server. @everyone itself is opt-in on top of that, with its own tick, because it is the one mention nobody should send by accident.

    The member picker is filled from accounts linked here, topped up from your guild when the privileged Members intent happens to be enabled — so it works either way rather than requiring a trip to the developer portal.

    Auto-role and reaction roles

    An auto-role is handed to everyone who joins. A reaction role binds one emoji on one message to one role, keyed on the pair since a message normally carries several choices; the emoji is stored in the shape the gateway reports it, so matching is a string equality rather than a guess. Adding a binding also puts the emoji on the message, and says so when it could not.

    Both failure paths log the real cause, which is almost always the bot's own role sitting below the one it is trying to grant.

    Support tickets

    They work the way Ticket Tool does. Post a panel into a channel and it carries a button; pressing it asks what the problem is, then opens a private channel that only that person, your staff role and the bot can see. Closing it asks once, deletes the channel and keeps the record in the panel — a Discord that accumulates two hundred dead #ticket-0042 channels is worse than no ticket system at all, which is why the record lives here rather than there. One open ticket per person. The bot needs Manage Channels.

    Without a staff role every ticket is private to the person who opened it, which is almost certainly not what you want — the picker says so.

    /profile

    Anyone who has linked their account can run /profile in your server and the bot answers with their GameBlade profile: their avatar, how many games they have, hours played, achievements, friends, when they joined and what they are playing right now. The avatar travels as an attachment rather than a link, because the media route needs authentication and opening it to the world to save a round trip is not a trade worth making. Someone who has not linked is told how to.

    The command is registered against your server rather than globally, so it appears the moment the bot connects instead of up to an hour later.

    Configuration and testing

    The bot needs a token, a channel and this server's public address. The address is for cover art: Discord fetches images itself, so a relative path would resolve against discord.com. Paste the bare token from the Bot tab; a token pasted as Bot <token> is accepted too.

    Test walks every step between that token and a message arriving — the token itself, whether the bot was ever invited to your server, whether it can see the channel you named, and whether it may post there — and reports each separately, because those are the things that actually go wrong and they all look identical from outside. A passing run leaves a test message in the channel.

    It can post whatever you type, announce newly added games every fifteen minutes, and announce requests as they are granted. Turning announcements on starts from that moment rather than posting everything already in the catalog, and only games whose metadata matched are announced — an unmatched entry is a folder name with no cover and no blurb.

    Discord publishes no friends list to third-party applications. There is no scope for it and no endpoint. "Friends from Discord" therefore means other players here who are in the same server as you, which is the closest the platform allows — and since linking pushes everyone into that one server, very nearly the same set.

    Theming and the landing page

    Theming

    Ten presets — eight dark (Midnight, Slate, Carbon, Nebula, Aurora, Ember, Moss, Oceanic) and two genuine light ones (Daylight, Parchment) — plus an optional accent colour that replaces the preset's own. Only the mid step is picked; the lighter and darker steps are derived from it, so hover, focus and gradient states keep working without asking anyone to choose four related colours by hand.

    A theme is a complete surface ramp rather than one hue: brightening only the accent on a near-black chrome produces something that reads as broken. The tokens are resolved server-side and applied by both the web app and the desktop client, so a server's look is one setting rather than two that drift.

    Players can disagree. The client's Settings → Appearance offers the same ten themes and the same accent picker, stored in that machine's settings file. Picking one overrides the server's for that PC only; Follow the server hands it back. An operator chooses the look of their archive, and nobody has their desktop restyled the next time that choice changes.

    Editing the landing page

    Admin → Appearance → Landing page turns the landing page into an ordered list of sections. Add, reorder, hide and edit them with the real page rendering beside the form; the preview is the same component the public page uses, not a mock-up of it.

    Section
    HeroThe headline, with an eyebrow line, a background image and its dimming, alignment, and four heights up to full-screen.
    Feature gridShort "what you get" cards, two to four across, as cards or plain.
    How it worksA numbered sequence — get an invite, install, play.
    StatsA strip of numbers, optionally including the live game count.
    ScreenshotsA grid, two to four across, in widescreen, ultrawide, square or poster shape.

    Every section also has its own padding, background (none, a muted band, or an accent wash) and content width. Alternating those is most of what makes a page read as designed rather than as a stack of boxes, and all three come from theme tokens — so a light theme gets a light band rather than a dark stripe.

    Blocks rather than free-form positioning is deliberate: an operator says what the page contains and in what order, while each section's layout stays something that was designed once and works at every width, phones included. Operator copy is rendered as text and never as HTML, only YouTube can be framed, and a stored page that cannot be parsed falls back to the built-in one rather than taking the front door down. Reset restores the shipped page at any point.

    Publishing the Windows client

    Admin → Settings takes the installer itself: pick a .exe (or .msi, .msix, .appinstaller, .zip) up to 1 GB and it is stored on the server and served from the landing page's download button, with its size shown alongside the version. One build is kept at a time — uploading again replaces it.

    CLIENT_DOWNLOAD_URL and the URL field beside the upload still work and are used whenever no installer has been uploaded, so an existing deployment keeps pointing wherever it already did.

    Bandwidth, health and backups

    Bandwidth

    Two limits, both off by default (0 means no limit), under Admin → Settings:

    • A download speed cap in KB/s, applied per stream. A client opening several connections gets that much on each, which is the honest way to describe it.
    • A monthly allowance per account, in MB, resetting on the 1st. Override it for one account on the Users page — an explicit override binds even for an administrator, while the server-wide default deliberately does not apply to them, so a default can never lock the operator out of their own downloads.

    An account over its allowance is refused with 429 before any bytes are sent, and a single transfer that would cross the line is cut off mid-stream — usage is only recorded when a stream closes, so a start-only check would let one oversized download sail straight past.

    Health

    Admin → Insights → Health answers "is anything wrong", which analytics does not: disks running out, games that have gone from disk, entries with no launch or save rule, games tracking achievements they cannot sync, files whose contents no longer match their recorded checksum, accounts that have hit their limit, unanswered bug reports, and when the library was last scanned. Every finding links to where it is fixed. It is all derived from rows already being written, so there is nothing to keep in step by hand.

    Backups

    An archive holds the database, every player's cloud saves, uploaded media and the published installer — the things that exist nowhere else. The game library is deliberately left out: it is enormous, you already have it, and a scan rebuilds the catalog from it. Cached artwork is out too by default, being both the largest part and the one part that can be fetched again.

    The database is copied through SQLite's own backup API rather than by copying the file. Under WAL the file on disk is not a complete database on its own, and copying it during a scan produces an archive that restores to a corrupt state.

    Written every backupEveryHours hours keeping backupKeep of them, or on demand. To restore: stop the server, unzip the archive over an empty DATA_DIR, start it again.

    The external API

    A versioned, key-authenticated API at /api/v1 for driving the server from elsewhere — provisioning accounts from a billing system, handing out invites, reading stats. Keys carry explicit scopes, and users:admin is separate from users:write so a provisioning key cannot mint itself an administrator.

    Full reference, including a worked provisioning example: docs/API.md.

    Layout

    apps/server     Fastify API, scanner, metadata, social, saves, achievements, messaging
apps/web        Public landing page and the admin panel (React 19 + Tailwind)
apps/desktop    Tauri v2 client: the tabbed UI plus Rust install/launch/sync

    The database schema lives in apps/server/src/db/schema.ts, with plain-SQL migrations applied at boot from apps/server/src/db/migrations.ts. Append a new migration rather than editing an applied one.

    Building a Windows release by hand

    The Windows client is built on demand rather than on every push. Both Actions workflows can build it — run Publish manually and tick build_client — but neither does so on its own, because Windows minutes bill at twice the Linux rate and a full client build is long enough that doing it on every push would dominate the budget for something most pushes do not ship.

    scripts/build-windows.ps1 does the same job on any Windows machine with Node 22, pnpm and the Rust toolchain: 

    .\scripts\build-windows.ps1

    It asks for the version, stamps it across every manifest that carries one — the five package.json files, tauri.conf.json, the Rust crate and its lockfile, which are read by different things and must agree — then typechecks, tests, builds, and copies the .exe and .msi into dist/windows/<version>/.

    scripts/build-windows.cmd is a double-clickable wrapper, which also avoids the execution-policy prompt. It always waits for a keypress before closing, so a failure cannot vanish with the window; set GAMEBLADE_NOPAUSE=1 to skip that when scripting it. Every run is transcribed to build-windows.log at the repo root.

    Flag
    -Version 0.5.3Skip the prompt.
    -KeepVersionBuild at the current version, changing no files.
    -FastDrop link-time optimisation. Much quicker; not for release.
    -SkipChecksSkip typecheck and tests.

    Only the client is built — the server ships as a container image built on Linux. Commit the version bump and tag it once the installer is in hand; the tag publishes the release and the image, and you attach the .exe to it.

    If the window opens and closes doing nothing, it is almost always a missing prerequisite. Open PowerShell in the repo and run the script directly to see the message — it names every missing tool at once rather than one per run. The usual culprit is that a tool is installed but the terminal predates the install: a running process keeps the PATH it started with, so open a new one.

    Security notes

    • Passwords are hashed with Argon2id using OWASP's low-memory profile.
    • Session tokens are opaque and stored only as SHA-256 hashes.
    • State-changing requests from the browser require a CSRF header; bearer-token requests from the desktop carry no ambient authority and are exempt.
    • Every download path is re-resolved against its library root and symlink-checked before any bytes are served, so a crafted path cannot escape the mount.
    • The container runs as a non-root user and the library is mounted read-only.
    • Archive entries are attacker-controlled, so both the game installer and the save restorer rebuild every path from its normal components and reject anything containing .. or a root — the zip-slip escape.
    • Uploaded saves are verified against the digest the client declared before the version is accepted, so a truncated transfer never becomes the copy others pull.
    • Profile visibility is applied when a summary is built, per viewer, so a friends-only profile never leaks its current game to a stranger.
    • Messages are stored as text the server can read; membership is checked on every read and write, and messaging is friends-only. What that does and does not mean is set out under Messages.
    • Outgoing Discord messages carry an explicit mention permission list, so text the server did not write cannot cause a notification.
    • Profile links are checked for an http(s) scheme on both sides, since the value lands in an href on a page other people open.
