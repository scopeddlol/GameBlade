GameBlade

Current deployment and operator guide for version 0.8.

Architecture

GameBlade can run on one machine or as a Coordinator with one or more Nodes. A public reverse proxy may expose the Coordinator. Nodes never need an inbound game-transfer port.

Desktop
parallel HTTPS ranges
Coordinator
authorizes, verifies, streams
Node
outbound authenticated HTTPS

For each Desktop byte range, the Coordinator selects a Node known to hold the game and queues a 10 MiB ZIP chunk request. The Node reads and verifies the chunk, posts it to the Coordinator, and the Coordinator verifies it again before streaming it to Desktop.

Every install is one ZIP64 package. The Desktop keeps several ranges in flight, writes chunks at their offsets, records resume journals, verifies hashes as bytes arrive, and automatically unpacks the completed package with a bounded parallel worker pool.

One-machine quick start

git clone https://github.com/scopeddlol/GameBlade.git
cd GameBlade
cp .env.example .env
# Set LIBRARY_PATH in .env
docker compose up -d

Open http://<host>:8080, create the first administrator, and let the read-only library scan.

Image Purpose

gameblade-node Scans mounted libraries and supplies chunks through outbound HTTPS.

Coordinator and reverse proxy

Start with docker-compose.coordinator.yml. Caddy, Pangolin, Cloudflare Tunnel, or another HTTPS reverse proxy can publish port 8080 normally. Set TRUST_PROXY=true and keep SECURE_COOKIES=auto. WebSocket forwarding is needed for live social features.

No extra UDP service is part of downloads. The public proxy carries Coordinator HTTPS, including download responses and Node long polls.

Set up a Node

  1. Copy docker-compose.node.yml to the machine holding the games and update its read-only volume.
  2. Run docker compose up -d.
  3. Create a code in Admin → Nodes → Enrolment.
  4. Open the Node's local page on port 8080 and enter the Coordinator HTTPS URL and code.

The code is spent after registration. Unused codes can be deleted. Nodes can be renamed inline from Fleet. Nodes store identity in /data/node-state.json; back that file up.

The local Node control center has three workspaces. Overview shows mounts, reporting, scan progress, and hashing progress. Game intake is a file-browser view of every top-level folder and supported archive: approve an entry to record an explicit decision, ignore it to withdraw it from the Coordinator and future scans, or reset it to automatic behavior. These actions never alter the read-only game disk.

Backups keeps complete Coordinator recovery archives on the Node. A copy includes SQLite, settings and config state, every cloud-save version, uploaded media, the published client, and cached artwork. Use Back up now to force a new one; otherwise the Node keeps a fresh daily copy automatically and retains the newest seven in /data/coordinator-backups. Size the Node's writable /data mount accordingly. Game packages are not duplicated inside these archives because the Nodes already hold them. 

# Several libraries
volumes:
  - /mnt/3TB:/libraries/3TB:ro
  - /mnt/E:/libraries/E:ro

Admin operations

  • Fleet: state, coverage, transfer totals, rename, library assignment, block, and remove.
  • Analytics: total Coordinator delivery, Node-backed share, coverage, busiest Nodes, and popular games.
  • Enrolment: create and delete unused one-time codes.
  • Catalog: the “Games with no Node” tile opens the affected games for removal.

Desktop connection cards show friendly Node names only. They never display Node, client, or Coordinator addresses, hostnames, domains, or ports.

One game, several machines

A game can be held on more than one machine. Moving a library onto a VPS used to create a second catalog entry for every game in it — a Node reports into a library of its own, because relative paths only mean anything within one — so the Store showed the archive twice and the new copies carried none of the achievements, saves or playtime of the originals.

Copies are now folded into the entry that already exists. Nothing is deleted: the folded-in row keeps its library, path, files and chunk hashes, so its machine goes on serving them, and it simply stops being an entry of its own. Downloads then follow the game rather than the machine — the Coordinator picks the package the most online hosts agree on, addresses each host in the ids that host knows its own copy by, and a chunk comes from whichever is up.

Only proof merges on its own: identical package bytes, or the same package name at exactly the same size. Weaker evidence — the same identified game at two different sizes, which is either two builds or a bad copy — is listed in Admin → Catalog → Duplicates with the sizes, paths and hosts shown, and merged only when somebody says so. The same page lists what has already been folded together and can separate any of it again.

Deleting the local copy after a move does not flag the entry as missing while another machine still holds one. When the last copy goes, it is marked honestly.

Direct downloads from a Node

Every transfer used to be relayed: the Desktop asked the Coordinator, the Coordinator pulled the chunk over the Node's outbound connection and streamed it onward. That is the only thing that works for a machine behind a home router, and it spends the Coordinator's uplink twice for every byte — which on a small VPS is the ceiling on everyone's downloads.

A Node that can be reached on its own address now serves clients itself. Set the address on the Node's own page under Direct downloads, or with GAMEBLADE_PUBLIC_URL; the listener opens on port 8099 unless GAMEBLADE_PUBLIC_PORT says otherwise, and clearing the address closes it again. Changes take effect within a heartbeat, without a restart.

The Coordinator hands a client the address together with a signed grant naming one Node, one file and an expiry. The Node checks that grant against the Coordinator's public key, which it receives at registration and on every heartbeat, and can never mint one itself. Chunks are named by their SHA-256 and verified on arrival exactly as before, so a direct source cannot serve different bytes than the relay would — only faster ones. Bytes delivered this way are reported back, so allowances and Node statistics stay correct.

Put TLS in front of that port if you can — a reverse proxy, or the one already publishing the Coordinator. The bytes themselves are hash-verified either way and a grant is worth one file for a few minutes, so plain HTTP is a considered trade rather than a hole; but on an https:// address nobody on the path can read a grant at all.

The relay remains the fallback for every client, every Node without an address, and every moment a direct fetch fails. A source that fails twice in a row sits out the rest of that download.

Download behavior

  • One ZIP64 package per game, cut into fixed 10 MiB chunks with up to eight concurrent HTTPS requests by default.
  • Resume journals survive restarts; transient failures retry with backoff.
  • Chunk SHA-256 is checked at Node, Coordinator, and Desktop. A package is never offered until every 10 MiB chunk has a hash on the current grid.
  • Quotas and speed limits are enforced once at Coordinator, without double-counting Node source records.
  • If one Node fails, Coordinator tries another current holder before returning unavailable.
  • Where a game is held on several machines, the Desktop spreads chunks across them in proportion to what each is measuring — re-decided per chunk, so a host that saturates loses its share within seconds.
  • Test download speeds on a game's page measures every host by moving a couple of megabytes over the real route. Results are shown to the player and reported back, so the next person starts with an order somebody has actually tested.

Troubleshooting

Node is not Active Confirm outbound HTTPS to the exact Coordinator URL. Check the Node page and container logs. No inbound Node port is required.
File is no longer available Confirm the game is in an online Node catalog and every file is fully chunk-hashed.
Node backup failed Confirm the Node is enrolled, can reach the exact Coordinator URL, and has enough free space in its writable /data mount. The Backups workspace retains the last error and can force a retry.
Catalog is too large Use current Node and Coordinator images. Catalogs upload in bounded batches and catalog routes accept large reports.
Download is slow Press Test download speeds on the game's page in the client: it measures each host separately and says which is the bottleneck. Then check Node disk, Node uplink, Coordinator egress, configured limits, and Desktop concurrency.
A game is listed twice Two machines hold copies that do not agree byte for byte. Open Admin → Catalog → Duplicates, compare the sizes and paths, and merge them into whichever entry should keep its achievements and playtime.
Direct downloads are not being used Check the Node's page shows a public address, that the port is reachable from outside (try /gb/v1/health on it), and that Admin → Nodes marks the Node direct. Downloads keep working through the Coordinator either way.

Development and releases

Use Node 22, pnpm 10, and a current Rust toolchain.

pnpm -r typecheck
pnpm -r test
cargo test --manifest-path crates/gameblade-mesh/Cargo.toml

The publish workflow builds standalone, Coordinator, and Node images plus Windows installers.
