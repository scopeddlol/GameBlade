GameBlade 0.6.7 GitHub API reference

    GameBlade

    A self-hosted platform for preserving free-to-play and DRM-free games: a Docker server that holds the archive, and a Windows desktop client that makes playing from it feel like a modern game launcher.

    This page is the whole manual. The README is deliberately short — it exists to get a server running and to point here. Everything below is one file with no build step: open it in a browser to read it, open it in an editor to change it.

    Server, not a web app

    The server hosts the files, a public landing page and an admin panel. Everything a player does happens in the desktop client.

    Read-only by design

    Your library is mounted :ro. GameBlade indexes and serves it; it never writes to it.

    Invite-only

    Self-registration is off by default. Accounts come from invite codes an administrator generates.

    Small

    One Alpine container, SQLite, no external database or cache.

    A node can hold several drives, and you can watch the fleet.

    • “Connect this node” did nothing. The setup page's script was inline, and this server sends script-src 'self' on every response, so the browser dropped it — silently. The page rendered, the button depressed, and nothing was sent or logged. It is served as a file now. See looking at a node.
    • More than one library on a node. Mount each drive under /libraries and the directory name becomes the library's name. /library still works for one. Mounting two at the same path never did — Docker keeps one and drops the other, with no error anywhere. See a node with several drives.
    • Scanning and hashing from the node's own page, with live progress, instead of waiting for timers. See looking at a node.
    • Nodes is its own section of the panel, with per-node statistics, fleet analytics, and a live map of the tunnels. See Nodes.
    • A coordinator no longer offers libraries or a scan. It has no disk, and scanning an absent path flagged the entire catalog its nodes had just reported. Both are gone from its panel and refused by its API. See the roles.

    Pairing a node is now the only step there is, and the mesh actually turns on by itself:

    • Hashes a node computed after it first reported were being dropped. Hashing changes nothing a report compares — not size, not file count, not modification time — so every game came back “unchanged” and the afternoon's work went in the bin. A coordinator that had never been a standalone server never had one eligible game, and nothing said so.
    • A node gets its library when it registers, named after it. No creating one by hand, no path that does not exist, no coming back to assign it. See libraries.
    • A node takes the hashes the coordinator already has instead of re-reading terabytes to arrive at the same numbers. See hashing.
    • Nodes keep their outbound tunnel mapping alive, so Desktop can establish an encrypted Node-to-Client path after any amount of idle time. No node UDP port is published or forwarded, and game bytes never pass through the coordinator.

    A coordinator and its nodes actually assemble now, and setting one up is a page rather than a compose file:

    • One image per role. gameblade-coordinator and gameblade-node alongside the standalone gameblade. Pulling one has already said what it is, so there is no ROLE to set — and a node is one container rather than two, because the scanner and the mesh agent are an implementation detail rather than something to keep in step by hand. See the roles.
    • A node sets itself up from its own page. Bring it up with nothing configured, open it, and give it the coordinator's address and an enrolment code. No environment variables, no restart. See connecting a node.
    • It stays connected. A rejected credential is now something both halves of a node recover from by themselves, rather than a node that looks healthy and serves nothing until somebody restarts it. See staying connected.
    • Four things that made the split topology impossible — a node that could not enrol, could not hash its own games, a coordinator that would not accept a library and then scanned it — are fixed. If you built one on 0.6.1 and worked around them, what to undo.
    • Releases come from CI. The PowerShell build scripts are gone; a tag builds the images and the Windows client and publishes them together. See cutting a release.

    What’s new in 0.6.1. A short release, and all of it is the 0.6 infrastructure being made to work rather than anything added on top:

    • Sharing a download now works on Windows. It never had. A seeding client bound its socket in a way Windows accepts and then quietly refuses to deliver IPv4 traffic to, so a player who switched sharing on was unreachable — indistinguishable, from the outside, from a player who had nothing to offer. See letting players share.
    • A node has a page of its own instead of the coordinator’s admin panel over an empty database. It says what it scanned, what it can serve, and whether the coordinator is hearing from it.
    • /api/health names the role. Three containers used to answer it identically.
    • A node’s catalog report is one transaction, so a report that fails halfway no longer leaves the catalog halfway written.
    • The client’s own tests now pass on Windows, where two of them had been failing — which, for a client that only runs on Windows, is everywhere that counts.
    • Node 24 is refused rather than discovered. The database driver aborts on it; the image and CI have always run Node 22. See development.

    Setting one up. If you are building the split topology rather than reading about it, a coordinator and two nodes, in production is the whole build in order — Caddy in front, the nodes on a LAN, their status pages reachable from outside. Four things stood between a fresh coordinator and a client downloading a game in 0.6.1 and none of them do now; if you built one on 0.6.1 and worked around them, what to undo.

    And in 0.6.0, if you are coming from 0.5. This is where GameBlade stopped being one machine:

    • Three roles from one image — standalone, coordinator, node, chosen with ROLE. 0.6.2 gave each its own image instead; a standalone server behaves exactly as it always has either way.
    • Clients download straight from the machine holding the files, over QUIC, verified a chunk at a time.
    • A process-local private overlay: coordinator rendezvous, then encrypted QUIC directly from node to client.
    • Players can serve pieces to each other, off by default at both ends.
    • mesh-doctor, which answers “can a client actually reach this machine” before anything is deployed.

    How the pieces fit

    Piece Who uses it What it does
    Server (Docker) You Reads the library from disk, serves the API, stores saves and profiles
    Landing page (/) Everyone Explains the archive and links the Windows client download
    Admin panel (/admin) Administrator Invites, users, catalog, metadata, featured games, settings
    Desktop client (Windows) Players Home, Library, Store, Requests, News, Social, Messages and Settings
    Node (ROLE=node) You Holds the game files, scans them, reports upward, and serves bytes straight to clients. Has a status page and nothing else.

    There is deliberately no web library browser — that lives entirely in the desktop client. A player who signs in on the web lands on an account page (username, email, password, signed-in devices) instead.

    Where to get it

    Both halves come out of the same release, built by CI and published together: the four images, and the Windows installers attached to the release itself. Nothing is built by hand any more — see cutting a release. Keep a client and its server at the same version; that they are produced by one run is what makes that the default rather than something to remember.

    Server images ghcr.io/scopeddlol/gameblade for one machine, plus -coordinator and -node for the split topology. A legacy -relay image is also published for older Desktop builds. latest and a tag per release on each. linux/amd64, and linux/arm64 when a release asks for it.
    Windows client The .exe on the latest release. An .msi is there too for deployment tooling.

    Getting it running

    git clone https://github.com/scopeddlol/GameBlade.git
cd GameBlade
cp .env.example .env

    Edit .env and set at least LIBRARY_PATH. Then:

    docker compose up -d

    Open http://<host>:8080 and create the first administrator account. That first-run screen is only available while the database has no users.

    Once the library has scanned, upload a client build from Admin → Settings (or point CLIENT_DOWNLOAD_URL at one hosted elsewhere) and invite people from Admin → Players → Invites.

    If it fails to start with a database error, the data folder is almost certainly owned by root while the container runs as uid 1000. SQLite is built into the image — nothing to install — it just cannot create its file: 

    sudo chown -R 1000:1000 ./data

    Alternatively set user: "1000:1000" on the service to match your own id -u/id -g.

    What a library looks like

    Anything at the top level of a library root is treated as one game — either a directory or an archive. Nested folders are indexed as that game's files, not as separate games. 

    /mnt/games/
├── Hollow Knight/            <- folder game
│   ├── hollow_knight.exe
│   └── data/
├── Stardew_Valley_v1.6.8/    <- folder game; version stripped from the title
│   └── Stardew Valley.exe
└── Celeste v1.4.0.0.zip      <- archive game

    Titles are cleaned before metadata lookup: version markers (v1.6.8, Build 12345), bracketed tags ([GOG], (2015)) and release-group noise (Repack, FitGirl) are removed. Dotted acronyms such as S.T.A.L.K.E.R. survive intact. Anything matched wrongly can be corrected by hand from the game's page.

    Configuration

    Everything is read from the environment at boot. Nothing here is required except a library path on an instance that has one — and, on a node, the coordinator to report to. Values set in the admin UI take precedence over the environment, so credentials can be seeded from compose and changed later without touching the stack.

    LIBRARY_PATH and LIBRARY_PATHS are two different things, and the quick start uses the first while everything below documents the second. LIBRARY_PATH and HTTP_PORT live in .env and are read by Compose, to decide what to mount and what to publish on the host. LIBRARY_PATHS is read by the server, and names roots inside the container — which is why it is /library in every example here regardless of where the games actually are. Nothing in this section is a Compose variable.

In 0.6.1 it did scan them, which flagged every game its nodes had just reported; turning both off was mandatory then and is a no-op now.

    The mesh agent

    The agent is a separate process from the server, and reads its own variables rather than the server's. It is what actually serves game bytes to clients over QUIC. In the gameblade-node image both run in one container under a shared entrypoint, so none of this normally has to be set — it is here for anyone running the agent somewhere else.

    VariableDefaultPurpose
    GAMEBLADE_SERVERfrom the state fileThe coordinator's base URL. Unset, the agent waits for the setup page to supply one rather than exiting.
    GAMEBLADE_LIBRARYthe mountsLibrary roots inside this container, read-only — one path or a comma-separated list. Left unset the agent reads the same two places the server half does, so both halves agree about what this machine holds without being told twice. Nothing mounted anywhere is a warning rather than an exit: a wrong volume is fixed by editing compose, which is easier against a node that is running and saying so.
    GAMEBLADE_ENROLMENTfrom the state fileThe one-time code. The agent owns this node's keypair, so it is the process that registers; the setup page writes the code where it will find it.
    GAMEBLADE_STATE/data/node-state.jsonWhere the identity lives. Shared with the server process beside it — the node image points both at the same file.
    GAMEBLADE_PORT47820The node agent's internal UDP socket. The agent creates and maintains its mapping with outbound traffic; do not publish or forward it.

    The state file is the node. node-state.json holds the Ed25519 secret this machine is known by. Lose it and the node enrols again as a stranger, abandoning everything the coordinator knew about what it holds. It is the one file in a node's data/ worth backing up; everything else there is a rescan away.

    Ports, and which of them matter

    PortWhereForwarded?
    8080/tcp Coordinator or standalone HTTP Behind the reverse proxy. Publish it on the host only for direct or LAN access.
    8080/tcp A node's own status page LAN or tunnel only. It is unauthenticated — never straight onto the internet.
    Outbound UDP Node and Desktop private tunnel No published or forwarded port. Both sides establish the mapping from inside their own network.

    Running behind a reverse proxy

    Required in every case

    Set TRUST_PROXY=true. Without it every request appears to come from the proxy, which breaks per-client rate limiting and logs the wrong address.

    SECURE_COOKIES=auto (the default) marks session cookies Secure when the proxy reports X-Forwarded-Proto: https.

    On its own hostname

    Nothing else to configure. Point the proxy at http://gameblade:8080 and leave BASE_PATH empty.

    Under a sub-path

    Set BASE_PATH=/gameblade. The web client ships relative asset URLs and reads its own base path from a <base href> tag the server rewrites per request, so the same image works at / and at any sub-path with no rebuild.

    Do not strip the prefix at the proxy — GameBlade expects the full path.

    What every proxy in front of this has to get right

    Four things, and they are the same four whichever proxy it is. Everything after this section is those four spelled out in one syntax or another.

    • Pass the forwarded headers, and set TRUST_PROXY=true so they are believed. Both halves, or client addresses are wrong in a way that is invisible until rate limiting buckets every player together.
    • Do not buffer responses, and do not compress them. A download is already-compressed bytes, so buffering adds latency and memory pressure and compression adds CPU for nothing. GameBlade says so on every download response with Cache-Control: no-transform and X-Accel-Buffering: no.
    • Allow long responses and large bodies. A multi-gigabyte transfer can run for hours, and an uploaded client installer can be 1 GB. GameBlade applies no request timeout of its own and no body ceiling beyond the per-kind limits; make sure the proxy does not either.
    • Let the WebSocket through. Presence, activity, notifications and new messages arrive on /api/realtime. Losing it costs freshness rather than correctness — everything it carries is also readable over REST — but a client that never gets it feels dead.

    Caddy

    Caddy needs the least said to it of any of them: it streams by default, applies no timeouts by default, imposes no request-body ceiling by default, and proxies WebSockets transparently. The whole file is this: 

    games.example.com {
        # Compress the panel and the API, and nothing else. Without a match,
        # `encode` would also compress game data — already-compressed bytes,
        # so it costs CPU on both ends and saves nothing.
        encode {
                zstd
                gzip
                match {
                        header Content-Type text/*
                        header Content-Type application/json*
                        header Content-Type application/javascript*
                        header Content-Type image/svg+xml*
                }
        }

        # Caddy sets X-Forwarded-For, -Proto and -Host itself. Pair it with
        # TRUST_PROXY=true on the container and nothing else is needed:
        # WebSockets, ranged requests and hours-long downloads all just pass.
        reverse_proxy 127.0.0.1:8080
}

    If the container is on a Docker network Caddy can see, use its service name instead of 127.0.0.1 and drop the published port from compose entirely, so nothing is reachable on the host at all.

    Do not add request_body max_size. Caddy has no body limit unless you set one, and the smallest thing that would break is a screenshot. The uploads that matter are the client installer (up to 1 GB), clips (512 MB) and save archives (512 MB). If your Caddyfile already sets one globally, exempt this site.

    Caddy cannot carry the mesh or a legacy relay. Both are UDP, and neither is HTTP — a reverse proxy has nothing to do with either. A forwarded UDP port goes through the firewall and the router, not through Caddy. See ports.

    Pangolin

    Pangolin tunnels traffic over WireGuard and terminates it in Traefik, so the container needs no published ports at all. Remove the ports: block from docker-compose.yml and point the Pangolin resource at gameblade:8080 on the shared Docker network.

    Two things matter for large downloads through a tunnel:

    • Do not enable response buffering or compression. Game data is already compressed, so buffering only adds latency and memory pressure. GameBlade sets Cache-Control: no-transform and X-Accel-Buffering: no on download responses to say so explicitly.
    • Allow long-lived responses. A multi-gigabyte transfer can run for hours. GameBlade itself applies no request timeout; make sure the proxy doesn't either.

    Tunnel throughput is the usual bottleneck on a large download. That is precisely what the desktop client's downloader — and, past that, the mesh — exist for.

    Pangolin in front of a node's status page

    A different job from the one above, and worth separating. The coordinator is a public service with its own accounts; a node's page is an unauthenticated internal readout you want to be able to look at from a phone without being at home. Pangolin is a good fit for the second precisely because the resource itself carries no authentication:

    • Put Pangolin's own authentication in front of it. The page has nothing worth stealing on it — counts, paths already in your compose file, and whether the coordinator answered — but it describes your infrastructure, and there is no sign-in behind it to fall back on. Whatever Pangolin offers, use it.
    • Point the resource at the node's HTTP port, either through an agent running on the node's own host targeting localhost:8080, or at the node's LAN address from elsewhere on the network.
    • Do not set BASE_PATH for this. Give each node its own hostname rather than a sub-path. A node's HTTP surface is three routes and a catch-all, and the catch-all answers with the same page, so a sub-path buys nothing and costs a rewrite that can go wrong quietly.
    • Nothing about the mesh goes through it. Game bytes never touch a node's HTTP port; they leave the agent beside it over UDP. Tunnelling this page has no effect on download speed in either direction.

    Keeping the page reachable over the LAN at the same time is the compose file's business, not the proxy's — see reaching a node's page two ways.

    The roles

    GameBlade is one build published as four images. Which one you pull is which thing you get; nothing has to be configured to make an image be what its name says, and an existing install that upgrades keeps behaving exactly as it did.

    ImageHoldsRuns where
    gameblade Everything: database, panel, and the games on local disk One machine. The default, and what GameBlade has always been.
    gameblade-coordinator Database, admin panel, landing page, API. No game files. A VPS. Small, because coordination is kilobytes.
    gameblade-node The game files. Scans them, reports upward, and serves them — both processes, in one container. Wherever the library lives.
    gameblade-relay (legacy) Nothing. A public UDP address and a table of paired sockets. Only beside a coordinator serving older Desktop builds. See the relay.

    The image is the role. docker pull of gameblade-coordinator has already said what that container is, so there is nothing to declare in a compose file and nothing to get wrong — a coordinator that was accidentally left as a standalone would scan libraries it cannot read and flag the catalog its nodes had just reported, and would look fine doing it.

    ROLE still exists and still overrides, for anyone who was already setting it. Nothing that worked on 0.6.1 stops working.

    A coordinator no longer offers what it cannot do. It has no disk, so the panel does not show it a library folder to add or a scan to start, and the API refuses both — a bookmark, an API key or a stale tab is enough to reach a route the navigation has stopped linking to.

    The scan in particular was not merely pointless. It walked a path that is not on that machine, read the empty result as “every game has been deleted”, and flagged the entire catalog its nodes had just reported. A coordinator's libraries are made for its nodes when they enrol and are managed under Nodes; each node scans its own disk from its own page. A standalone server is unchanged.

    Four images, one build. They are the same filesystem with different metadata on top, produced by one CI job from one Dockerfile, so a coordinator and its nodes cannot drift into disagreeing about the catalog they exchange — which is the failure separate builds would eventually produce. Pulling two of them onto one host pulls the layers once.

    Moving an existing install to a coordinator

    This is a copy, not a migration. The database is not converted or restructured; it is the same file, opened by the same code, on a different machine.

    1. Back up first. Admin → Insights → Health writes an archive of everything that cannot be recreated. Copy it somewhere that is not the machine you are moving off.
    2. Copy data/ to the new host. Copy, never move — the original stays where it is and stays whole.
    3. Start the coordinator with ROLE=coordinator and check it while the old instance is still the live one: sign in, browse the catalog, open a save, read a message. It will not scan the library paths the copied database still lists — the role sees to that — so there is nothing to switch off first.
    4. Enrol the node that holds the games, choosing the library its games are already in under Reports into on Admin → Nodes → Enrolment. Choosing it on the code rather than after the node registers is the point: assigning it afterwards is a race the node wins, and the catalog everything is attached to is orphaned before you get there.
    5. Point the proxy at the coordinator only once all of that looks right. If anything is wrong, point it back — the old instance is untouched.

    One advantage worth knowing about: a coordinator migrated from a standalone server inherits the chunk hashes that server computed, so hashing a node's library is a step you have already done. A coordinator built from nothing has not.

    Assign the right library. A node's catalog is matched into a library by relative path, so reporting into the library those games are already in updates those entries and every game keeps its id — and with it every achievement, save rule, artwork match, favourite and playtime record. Pointing a node at a different library would add the whole catalog again as new games and leave all of that attached to entries nothing references. Reports are refused until a library is assigned, precisely so this cannot happen by accident.

    Legacy relay

    The relay binary remains available for compatibility with older Desktop builds. Current Desktop builds never request it: downloads establish a private direct tunnel from node to client, and no game byte is proxied through the coordinator or a relay.

    It is the least clever component here on purpose. It never terminates TLS, never parses a chunk request, never learns which game is moving through it, and holds nothing but a table of which two sockets belong together. The QUIC session runs end to end between the client and the node, so what passes through is ciphertext it could not read if it wanted to — and every guarantee made elsewhere survives untouched: the client still pins the node's identity, the node still checks the grant, the client still verifies every chunk against its hash.

    It needs the coordinator's public key and nothing else. No database, no credentials, no API. Tickets are verified locally, which is what lets it be a small process next to the coordinator rather than part of it.

    Current Desktop does not use this path. It is strictly slower than a direct connection — an extra hop, over this host's pipe. Older clients may request it after a direct connection fails; relayed bytes count against the same allowance as any others, and GAMEBLADE_RELAY_MAX caps how many can be in flight so the exception path cannot quietly become the main road.

    RELAY_ENDPOINT is ignored by the current direct-only Desktop path. The default coordinator compose file does not run or expose a relay.

    Running one for a legacy client

    Legacy compatibility only. It is not present in docker-compose.coordinator.yml; if an older client still requires one, it can be added as a second service and fetches the coordinator's public key from the coordinator itself — waiting for it if it is not up yet, which it usually is not, because the two start together. 

      relay:
    image: ghcr.io/scopeddlol/gameblade-relay:latest
    container_name: gameblade-relay
    restart: unless-stopped
    depends_on: [coordinator]
    environment:
      GAMEBLADE_SERVER: http://coordinator:8080
      GAMEBLADE_RELAY_MAX: '256'
    ports:
      - '47821:47821/udp'

    Ordinarily there is nothing else to set: the coordinator tells clients to use the hostname they already reached and UDP port 47821. If the relay has another public address, set RELAY_ENDPOINT on the coordinator — not on the relay — to that host:port. 

    RELAY_ENDPOINT=games.example.com:47821

    Then open 47821/udp on the host firewall. The reverse proxy is not involved — this is UDP and it is not HTTP, so Caddy has nothing to do with it.

    A hard network boundary still exists. Two peers behind incompatible symmetric or carrier-grade NATs cannot be guaranteed a direct route without either an inbound mapping or a data relay. GameBlade does not silently violate the direct Node-to-Client contract in that case; mesh-doctor identifies such a network explicitly.

    The coordinator's public key

    The relay fetches it and you never touch it. It is published, unauthenticated, at /api/mesh/coordinator-key — safe to be, because it is the public half: every client is handed it already, it verifies signatures and cannot make one, and the relay is given nothing else. No database, no credentials, no API.

    Setting GAMEBLADE_COORDINATOR_KEY directly still works, and is the answer for a relay running somewhere that cannot reach the coordinator over HTTP. The pair is generated on the coordinator's first boot and kept in its own database, so it survives restarts and image updates, and changes only if that row is deleted — at which point every node and relay picks the new one up on its next start.

    Looking at a node

    A node serves one page, about itself, on its HTTP port. It is not the admin panel and deliberately cannot be: a node owns no accounts, no settings and no catalog of record, so there is nothing on it to administer. What it can answer is the question people actually walk up to a node to ask — is this thing working? — and, since 0.6.4, it can start the two jobs that make it work.

    Before 0.6.4 the page’s script never ran at all. It was inline, and every response this server sends carries script-src 'self', so the browser dropped it and said so only in its own console. The page rendered perfectly, the setup form accepted what you typed, the button depressed, and nothing was sent — the page did not even refresh itself to hint that anything was wrong. If you are on 0.6.3 or earlier and Connect this node appears to do nothing, that is this, and the fix is the upgrade. Nothing about your node is broken.

    Every library root, its games, its size, and when each was last scanned Whether each volume mounted and the walk found anything — a drive that did not mount is marked as such, because otherwise it looks exactly like a drive with nothing on it
    Games ready to serve, out of games held How much of this machine the coordinator can actually hand out. A game is all-or-nothing over the mesh, so one unhashed file makes the whole game unservable — which is invisible in a files-hashed percentage sitting at 99.9%
    How many files have per-chunk hashes, out of how many Why a game that is plainly on this machine is not being served from it
    The last catalog report, and the reason if it failed Whether the coordinator is hearing from it at all

    Two buttons, because both of these used to happen only on timers. That is right for a node that has been running for a month and useless for one plugged in five minutes ago — nothing here is servable until its game is hashed, the first pass over a real archive is hours, and there was no way to start either or to see how far along they were except docker logs.

    • Scan now looks for mounts that were not there at boot, registers any it finds, and then walks every root. So a drive attached after the container started is found without restarting it.
    • Hash everything now reads every byte of every game that is not hashed yet. It stops between games rather than mid-file, so stopping it loses nothing — a game already hashed is skipped next time.

    Both show live progress, both refuse to start a second copy of themselves, and the page refreshes every three seconds while either is running instead of every fifteen. The timers still run underneath; pressing a button only brings the same pass forward.

    Route

    /api/node/statusThe same thing as JSON, for a dashboard or a script

    The JSON carries what the page renders: the coordinator it reports to and whether it enrolled, its node id, whether the agent's key exists yet, each library with its game count, size, last scan and whether its path is mounted right now, games ready to serve out of games held, hashed files out of total, the scan's progress, the hashing pass's progress, and the last report attempt with its reason if it failed.

    Keep it off the public internet. The page is unauthenticated, and it is given nothing worth authenticating — counts, paths already in your compose file, and whether the coordinator answered. There is no game data on it, no credentials and no key.

    Three things can be started from it — enrolment, a scan and the hashing pass — and each is bounded the same way: work this node already does on its own timers, brought forward. None of them reads out anything the page does not already show, none writes to the library (which is mounted read-only), none can be made to touch another machine, and starting a pass that is already running is refused rather than queued. So the worst a flood of requests achieves is a great many 409s.

    It is still about your infrastructure, so docker-compose.node.yml publishes it on 127.0.0.1. To reach it from elsewhere, put something in front that authenticates — a tunnel, and the LAN covers doing both at once.

    The mesh: a private Node-to-Client tunnel

    Without the mesh, every byte of every download crosses the proxy because the proxy is the only thing on the public internet. On a VPS with modest bandwidth that is the ceiling on how fast anyone can install anything. The mesh removes it: a client connects straight to a machine holding the files, and the server keeps doing the part that is actually small — saying who is out there and granting permission.

    The overlay is private and process-local. It provides the encrypted, identity-pinned route GameBlade needs without installing a system-wide network adapter. The coordinator introduces the peers and grants access; QUIC then runs directly between Node and Desktop. There is nothing for a player to install, approve or configure, and the coordinator never carries the game data.

    You can watch it working. Admin → Nodes carries the fleet, its analytics, and a live map of the tunnels. Current Desktop tunnels are direct; connection details shown to players use friendly node names and never expose an IP, hostname, domain or port.

    What a node is

    A node is a machine that holds game files and serves them to clients. The machine running the server is usually the first one. A node is known by its Ed25519 key rather than its address, because a machine on a home connection gets a new address whenever the lease renews.

    Nothing a node says is trusted. Its claim to hold a game is a hint about who to ask, not a promise; every chunk is verified against a hash this server computed, on the node before it sends and on the client before it is used. A node can be stale, wrong, offline or hostile and the worst outcome is a slower download. That is what makes enrolling one an operational decision rather than a security one.

    Turning it on

    1. Hash the games, on whichever machine holds the files. A game is only eligible once every one of its files has per-chunk hashes: without them a client cannot check a piece that came from somewhere else, so it will not accept one. The pass reads every byte once and produces the whole-file checksums at the same time, which makes the checksum pass redundant. On a node this happens by itself; on a standalone server it is an API call, not a button.
    2. Enrol the node. Admin → Nodes takes a name and a role and generates a one-time code. It is shown once and stored only as a hash; it expires in 24 hours and is spent the moment a node registers with it.
    3. Run the agent on the machine holding the files, and give it the code as GAMEBLADE_ENROLMENT. It registers, receives its own credential, and starts announcing what it holds.
    4. Assign it a library back on the Nodes page, if it is a ROLE=node server reporting a catalog rather than a mirror syncing one. Reports are refused until you do. See one library per node for why this matters more than it looks.
    5. Switch the mesh on under Admin → Settings → Server, in the Bandwidth card: Let clients download from mesh nodes. Until this is on, nodes may register and sync but no client is ever pointed at one — so a node can be enrolled and left to fill up first, and turning it on is a switch rather than a migration.

    Computing chunk hashes

    There is still no per-game button for this in the admin panel. The routes exist and work; nothing in the admin UI calls them. Anywhere this manual used to say Admin → Catalog → Games → Compute chunk hashes, it was describing a control that has never been there.

    A node is different, and since 0.6.4 has a button: it hashes its own library on a timer and its own page can start that pass now. This section is about doing it by hand on a standalone server, where hashing stays a deliberate per-game decision because the server can always serve the file itself.

    Three passes over a game's bytes, each answering a different question. All three are admin-only, run in the background, and refuse to start while another is running.

    CallWhat it does
    POST /api/games/<id>/chunks Per-chunk SHA-256 at 8 MiB, plus the whole-file hash. This is the one the mesh needs. Progress at GET /api/games/chunks/progress. Pass {"force": true} to redo a game that already has them.
    POST /api/games/<id>/checksums Whole-file SHA-256 only, so the client can verify a completed download. Progress at GET /api/games/checksums/progress.
    POST /api/admin/games/<id>/verify Re-hashes what was hashed before and records whether each file still matches. Findings surface on Health. Progress at GET /api/admin/verify/progress.

    The cleanest way to call them by hand is a device token, which is a bearer credential and therefore carries no CSRF requirement: 

    # Sign in as an administrator. Naming a device asks for a bearer token
# rather than a browser session.
TOKEN=$(curl -sS -X POST https://games.example.com/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"username":"admin","password":"…","deviceName":"hashing-cli"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["token"])')

# Every game, one at a time. `limit` caps at 200, so page through a larger
# catalog with `offset`. The route refuses while another pass is running, so
# waiting between them is the point rather than an inefficiency.
curl -sS -H "authorization: Bearer $TOKEN" \
  'https://games.example.com/api/games?limit=200&offset=0' \
  | python3 -c 'import json,sys; [print(g["id"]) for g in json.load(sys.stdin)["items"]]' \
  | while read -r id; do
      curl -sS -X POST -H "authorization: Bearer $TOKEN" \
        "https://games.example.com/api/games/$id/chunks"

      # Progress reports a state, not a boolean: idle, hashing or error.
      # Wait while it is hashing; idle and error both end the wait.
      while curl -sS -H "authorization: Bearer $TOKEN" \
        https://games.example.com/api/games/chunks/progress \
        | grep -q '"state":"hashing"'; do sleep 10; done
    done

    Revoke the device afterwards from Settings → Devices in the client, or leave it — it is a token like any other and is listed like any other.

    None of this applies to a node. A ROLE=node server has no API to call — a liveness probe and its own status page, deliberately, and nothing else — so it cannot be asked and does not need to be: it hashes what it scanned by itself. See hashing, which happens by itself. These routes are for a standalone server, where hashing stays a deliberate per-game decision because the origin can always serve the file anyway.

    Forward one UDP port to the node. This is the single cheapest thing you can do for reliability. Two machines both behind NAT have to punch a hole through it, which usually works and sometimes cannot — a symmetric NAT or a carrier-grade one defeats it. If one side is directly reachable, the problem essentially disappears regardless of what the other side is behind. Without a forwarded port, expect some players to quietly fall back to downloading through the proxy.

    What the server still does

    Coordination is kilobytes — keys, addresses, counters — which is why it fits on a small VPS. No game data is ever stored here for the mesh.

    Transfer allowances survive the change. A client is issued a signed grant carrying a byte ceiling, the node enforces it locally and reports back what it served, and those bytes count against the same monthly quota as anything downloaded from this server. A node that stops reporting is a node whose grants stop being renewed.

    A mirror announces the fingerprint of the copy it verified. When a game changes on the origin the fingerprint changes with it, and mirrors still announcing the old one stop being offered — no diffing, and no relying on a mirror to notice.

    Letting players share

    Let players share what they have downloaded is a separate switch, also off by default, and deliberately not implied by the one above. The first shares machines you run; this one turns players into distributors of each other's downloads, using their upload bandwidth. Each player must also opt in on their own client — Settings → Privacy → Share my downloads with other players, off until they say otherwise — and neither switch turns the other on.

    A sharing client serves only games it has fully installed, only to accounts holding a valid grant, and never to its owner. Every piece is re-checked against the manifest before it is sent, so an edited or modded install simply stops being a source. Turning the server switch off stops every sharing client within one heartbeat, without having to reach any of them.

    This did not work at all before 0.6.1. A sharing client bound its listening socket in a way Windows accepts and then declines to deliver IPv4 traffic to, so every player who switched sharing on was simply unreachable. There was nothing to notice: a peer nobody can connect to looks exactly like a peer with nothing worth having. If you tried player sharing on 0.6.0 and concluded it did nothing, you were right, and it was not your network. Update the clients.

    Finding out before you deploy

    Everything above rests on one question: can a client actually reach this machine directly? Two tools answer it, and both measure the NAT’s mapping behaviour rather than guessing from how many layers of it there are — double NAT is routinely punchable and single NAT routinely is not, so counting layers tells you nothing.

    ToolWhereNeeds
    mesh-doctor In every image, on PATH. docker exec gameblade-node mesh-doctor Nothing. It is already there.
    scripts/nat-check.py The repository. Run it on any machine you are considering. Python, and nothing else — no dependencies, no toolchain.

    Run one of them on a prospective node before enrolling it. If it reports the connection punchable, most clients will reach it directly. If it does not, that network cannot satisfy GameBlade's direct-only, no-inbound-port contract; moving either peer to a punchable network is the available remedy.

    When it does not apply

    All of these fall back to downloading from this server, and none of them are errors: the mesh is switched off, the client is an older build, the game has no chunk hashes, no node holds a current copy, or nothing would connect. The origin is always in the list of sources and can never be removed from it, which is what keeps the mesh an optimisation rather than something to depend on.

    A coordinator and two nodes, in production

    One coordinator behind Caddy, two nodes on your own network holding the games, and their status pages reachable both over the LAN and from outside through Pangolin. This is the whole build, in order, with the things that will bite marked.

    Nothing here needs working around. Four things in this path were unfinished in 0.6.1 — a node could not enrol, could not hash its own games, a coordinator would not accept a library, and then scanned the catalog its nodes had just reported. All four are fixed, so what follows is the build rather than the build plus four detours. If you already deployed on 0.6.1, see upgrading from 0.6.1.

    Three flows, and it is worth being clear which is which:

    • Everything a player does except downloading goes to the coordinator over HTTPS through Caddy. Kilobytes.
    • Each node tells the coordinator what it holds, outbound over the same HTTPS, every five minutes. Also kilobytes.
    • Game bytes go client ↔ node directly, over QUIC on UDP, touching neither Caddy nor the VPS. This is the entire reason for the split, and it is also the part with the most ways to fail — hence mesh-doctor before you commit.

    A coordinator holds no game files, so there is no HTTP fallback. On a standalone server, a client that cannot reach a node just downloads from the origin and nobody notices. Here the origin has nothing on disk. If the mesh cannot serve a game, that game cannot be downloaded at all. The private direct tunnel is the download path; the coordinator never substitutes itself as a data proxy.

    Upgrading from 0.6.1

    Skip this if you are building a new one. If you already have a coordinator and nodes running on 0.6.1, six things changed under you, and two of them mean undoing something you were told to do:

    ThenNow
    One image, with ROLE in every compose file, and a node as two services that had to agree about the library and the state path. An image per role, and a node in one container. ghcr.io/scopeddlol/gameblade still exists and is still the standalone server, so nothing breaks if you change nothing — but a coordinator or node is a smaller compose file now. Both shipped compose files have been rewritten.
    Joining a node meant putting COORDINATOR_URL and ENROLMENT_TOKEN in its environment and restarting it. A node with neither serves a setup form on its own page. Both variables still work and still win where set, so an existing node carries on unchanged.

    And, from 0.6.1 itself:

    ThenNow
    The two processes on a node wrote and read the shared state file in different casings, so the server never saw the agent's key, never enrolled and never reported a catalog. Both use the same names. A file written by the old agent is read as it is and rewritten in the new casing when the agent next registers, so the node keeps its identity and everything the coordinator knew it held. If you added duplicate camelCase keys by hand, leave them — they are what is read now, and the extra copies are ignored.
    A node had no way to compute chunk hashes, so nothing on it was ever mesh-eligible. A node hashes what it scanned, by itself, half a minute after boot and every ten minutes after that. Nothing to run. See hashing.
    A coordinator would not create a library unless the path existed inside its own container, so you mounted empty placeholder directories. A coordinator takes the path as the label it is. Unmount the placeholders — the library records keep working and nothing reads through them.
    A coordinator scanned those placeholders and flagged every game its nodes had reported, so SCAN_ON_START=false and SCAN_INTERVAL_MINUTES=0 were mandatory. The role decides. Both settings are ignored on a coordinator and it says so in the log at boot, so you can leave them, remove them, or set them wrongly without consequence.

    Update the coordinator and every node together. They exchange a catalog and a state file, and two of these changes are on both sides of that. Running a 0.6.1 node against an updated coordinator is not dangerous — it fails exactly as it failed before — but it will look like the fix did not work.

    1. The coordinator

    On the VPS. data/ is the only thing here that cannot be recreated, so it is the only thing to back up — and it is small, because no game files pass through this host.

services:

    No ROLE, no library mounts, and nothing about scanning: the image is the coordinator, it holds no files, and it will not scan. Only its HTTPS service goes through Caddy; there is no relay port to expose.

    2. Libraries, which you do not have to make

    A node gets a library when it registers, named after the node, and is assigned to it in the same breath. There is no step here for a new deployment — skip to connecting the node.

    It is worth knowing what that library is, because two rules follow from it and one of them decides whether a migration goes well.

    • A game already in a node's library keeps its id, and with it every achievement, save rule, artwork match, favourite, collection entry and playtime record. Reports are matched by relative path within the assigned library, so reporting again updates rather than re-adds.
    • One library per node, always. A complete report marks everything else in that library missing — a node says "here is everything I hold", and anything it did not mention is taken to be gone. Two nodes sharing a library would flag each other's games on every report, for ever. The automatic assignment gives each node its own, so this only becomes possible if you point two of them at one by hand.

    The path on a coordinator's library is a label. Nothing there ever reads through it, which is why an automatic one is /nodes/<node id> — and, since 0.6.4, why a coordinator will not let you create one by hand at all. There is nothing for it to be a path to.

    A node with several drives

    A node reads its own mounts. /library is one library, as it has always been, and every directory under /libraries is one more, named after the directory. Both forms work together and either works alone. 

        volumes:
      - ./data:/data
      # One drive, as before.
      - /srv/games:/library:ro
      # Or several, one mount each. The directory name is the library's name.
      - /mnt/3TB:/libraries/3TB:ro
      - /mnt/E:/libraries/E:ro

    Two drives mounted at the same /library is not an error to Docker. It keeps one of them and the other is simply never read, with no message anywhere — so the node reports half an archive and nothing says which half is missing. Before 0.6.4 there was no other way to say it, because the node image pinned LIBRARY_PATHS=/library; that pin is gone.

    LIBRARY_PATHS still overrides all of it for anyone who wants exact paths. Set, it is precisely what gets scanned and nothing is discovered underneath it.

    The mesh agent searches every root for a game rather than being told which one holds it, so bytes come out of whichever drive has them.

    All of a node's roots report into its one library on the coordinator. Paths from the second root onward are prefixed with that root's name, so two drives that both contain Hollow Knight stay two games rather than fighting over one row. The first root's paths are deliberately left alone: changing the path of a game that has already been reported would make it a stranger to the coordinator, which would add the whole catalog again and orphan every achievement, save rule and playtime record attached to the originals. Adding a drive adds games; it does not re-add the ones you had.

    A root whose mount has gone is disabled, not deleted. Deleting it would take its catalog with it, and a mount that failed on this boot is far more often one that will be back than a drive somebody meant to remove. Disabled means the scanner skips it, which is what stops one unmounted drive flagging every game on it as missing. It is re-enabled by itself when the drive returns.

    Taking over an existing library is decided on the code, not afterwards. When a node is replacing hardware, or you are splitting a standalone server into a coordinator and a node, pick that library under Reports into when you generate the enrolment code. Assigning it after the node has registered is a race you lose: the node reports into its new library first, and the catalog everything is attached to is orphaned.

    3. Connecting a node

    One container per machine holding games. It runs both halves of a node — the scanner that reports what is here and the agent that serves it — and needs nothing configured beyond where the games are. 

    # docker-compose.yml on each node
services:
  node:
    image: ghcr.io/scopeddlol/gameblade-node:latest
    container_name: gameblade-node
    restart: unless-stopped
    environment:
      TZ: Europe/London
    volumes:
      - ./data:/data
      # Change the left side. /library is where the image looks.
      - /srv/games:/library:ro
      # For a second and third drive, one mount each under /libraries.
      # The directory name becomes the library's name.
      # - /mnt/3TB:/libraries/3TB:ro
      # - /mnt/E:/libraries/E:ro
    ports:
      # The node's own page. Bound to this host's LAN address so it is
      # reachable from the network and from nowhere else.
      - '192.168.1.20:8080:8080'
      # Where game bytes leave this machine.
    security_opt:
      - 'no-new-privileges:true'

    The rest is a form. On the coordinator, open Admin → Nodes, give the node a name, pick the role Origin, and press Generate code. Then open the node's own page — http://192.168.1.20:8080 — and paste the coordinator's address and that code into the setup panel it is showing.

    That is the whole of it. The answers are written into data/node-state.json, both processes pick them up without a restart, and the page turns into the ordinary status readout once the node has enrolled. Nothing needs to be typed twice, and nothing has to be edited on the machine with the games on it.

    Repeat for the second node with its own enrolment code and its own data/. Each gets its own library automatically, which is what they must have — see libraries. One node holding several drives is a different thing and needs no second node: see a node with several drives.

    The form is a first-run screen and closes like one. It appears only while a node has not enrolled and is gone the moment it has, so an enrolled node has nothing a request can point somewhere else. It grants nothing by itself either — the enrolment code is checked by the coordinator, not by the node, so a wrong one produces a node that fails to register and says so. Keep the page off the public internet regardless: it is unauthenticated, exactly as it was before.

    If you would rather declare it than type it, COORDINATOR_URL and ENROLMENT_TOKEN still work and skip the form entirely. The environment wins where it is set.

    4. The state file

    data/node-state.json is the node's identity: an Ed25519 secret, the node id and token the coordinator issued, and the coordinator's public key. Both processes on the node read and write it, which is how they are one node rather than two — the agent generates the key and registers, and the server picks the registration up and reports against it. 

    {
  "secretKey": "…",
  "nodeId": "nod_…",
  "nodeToken": "…",
  "coordinatorKey": "…"
}

    Back this file up, and nothing else on a node. A node is known by its key, not its address or its hostname. Lose it and the machine enrols again as a stranger: a second node appears in the panel, the games it holds are attached to that one, and the entry that knew what the old one held is left pointing at nothing. Copy it if you ever move a node to different hardware. Everything else in a node's data/ is a rescan away.

    In 0.6.1 the two processes wrote this file in different casings and a node could therefore never report a catalog. A file from then is read as it is and rewritten correctly; there is nothing to do about it by hand.

    5. Hashing, which happens by itself

    Nothing is served from a node until its games have per-chunk hashes: a client will not accept a piece it cannot verify, so a game without them is never offered from anywhere but the origin — and on this topology the origin has no copy.

    A node does this on its own. Half a minute after boot, and every ten minutes after that, it hashes whatever it scanned and has not hashed yet, one game at a time, and the next catalog report carries the results up. There is nothing to run and nothing to enable.

    You can also start it now. The timer is right for a node that has been running for a month and useless for one plugged in five minutes ago, so the node's own page has a Hash everything now button with the count of games left on it. It runs the same pass the timer does — there is only ever one — and stops between games rather than mid-file, so stopping it loses nothing.

    It asks before it reads. The first thing a node does after pairing is ask the coordinator which of the games it holds are already hashed, and take those hashes rather than recomputing them. Hashes describe file contents, so a copy that matches is described by them exactly — and on a coordinator split off a standalone server, or one that already has another node holding the same games, that is the entire library and the hours disappear.

    Matched on relative path, then checked file by file on size, and adopted all-or-nothing per game. Anything that does not line up is hashed locally in the ordinary way, because adopting hashes for bytes this machine does not have would mean advertising a game and then failing every chunk of it.

    It waits forBecause
    The scanner to finish They would otherwise be reading the same disk at the same time, and the scan is what tells it which games exist.
    Games it has already hashed Skipped, from the chunk table rather than by re-reading. A restart resumes where it stopped instead of starting the archive again.
    Games flagged missing The files went away. Hashing one would fail once every ten minutes, for ever.

    Watch it on the node's own page: hashed files out of total climbs, and what the coordinator will offer is the games where those two numbers have met. It is a long job the first time — every byte of every game, at 8 MiB a chunk, so a multi-terabyte node is hours and is limited by the disk — and a short one afterwards, since only new and changed games need it.

    To do it on your own schedule instead, set AUTO_CHUNK_HASH=false on the node. Nothing then hashes anything, which means nothing is servable from it, so this is for an operator who would rather spend the disk deliberately — by starting the node with it on overnight, say — than have hours of reads begin after a scan.

    A game that changes on disk loses its hashes, and gets them back on the next sweep. A report replaces the file rows of any game whose size, file count or modification time moved, and the replacements carry whatever chunks the node sent. So a game you have just updated is briefly unservable — ten minutes at most, and longer only if it is large. Games nobody touched are reported as unchanged and are not rewritten at all.

    6. Reaching a node's page two ways

    The compose file above publishes the status page on the node's LAN address rather than 127.0.0.1, which is the whole of what is needed for http://192.168.1.20:8080 to work from anywhere on the network. Binding to the address rather than to 0.0.0.0 is deliberate: it keeps the page off any other interface the host happens to have, including a VPN or a second NIC.

    Pangolin then covers the outside, without changing any of that. Point a resource at the node — through an agent on the node's own host targeting localhost:8080, or at 192.168.1.20:8080 from elsewhere on the network — give it its own hostname, and the two paths coexist: the LAN one is a published port, the outside one is a tunnel, and neither knows about the other.

    Turn Pangolin's own authentication on for these resources. The page has no sign-in of its own and is not going to get one — a node owns no accounts to check against. It is a readout of your infrastructure, and the tunnel is the only thing between it and the internet.

    Leave BASE_PATH unset and give each node a hostname rather than a sub-path. A node answers on /, its own script, a handful of /api/node routes and a catch-all that returns the page again; a sub-path buys nothing over that and adds a rewrite that fails quietly.

    And nothing about game downloads passes through here. The bytes leave the agent over UDP on 47820; tunnelling the status page does not speed them up, slow them down, or route them anywhere.

    7. Making the nodes reachable

    This is the step that decides whether the whole thing works, so do it before you tell anyone the archive has moved.

    1. Measure first. docker exec gameblade-node mesh-doctor says whether a client can punch through to this machine. It measures the NAT's mapping behaviour rather than counting layers, which is the only thing that predicts anything — double NAT is routinely punchable and single NAT routinely is not.
    2. Do not publish or forward the mesh port. The node keeps an outbound NAT mapping alive from the same socket its private QUIC tunnel uses, and the coordinator synchronises both peers' punch attempts when a download begins.
    3. A stable LAN address is optional. A node is known by its key rather than its address, and each heartbeat replaces its connection candidates.
    4. Run mesh-doctor if a tunnel still cannot form. It distinguishes a punchable mapping from a symmetric NAT that cannot provide a direct path without violating the no-proxy contract.

    8. Checking it, in order

    The catalog arrives long before the games are downloadable, and this is normal. A node reports what it scanned within a few minutes, so the panel fills up almost at once — but a game is only servable once its files are hashed, and hashing a real archive is hours. In between, the catalog looks completely right and nothing will install, which on a coordinator means a download that fails rather than a slow one.

    This is the first thing that looks broken on a new deployment and is not. Hashed files out of total on each node's page is the number to watch; the games that can be served are the ones where those two have met. Leave it overnight for a large library.

    Staying connected

    A node and its coordinator are meant to stay joined for as long as both machines are up, and everything between them is built to survive the other end going away.

    What happensWhat it does
    The coordinator restarts, or the link drops Both halves retry. The agent's heartbeat and its held-open rendezvous poll reconnect on their own; the catalog report retries every ten seconds until it lands, then settles back to every five minutes.
    The node's public address changes Nothing. A node is known by its key rather than its address, and every heartbeat carries its current candidates — which is what makes a home connection a reasonable place to put one.
    The node's credential stops being accepted It registers again with the key it has always had, and is listed again within a heartbeat. No enrolment code is involved.
    Either half of the node crashes The container exits, and restart: unless-stopped brings both back together.
    The node is deleted from the panel It re-registers as a new node and needs its library assigning again. Blocking it, rather than deleting it, is the way to take one out of service.

    A rejected credential used to be permanent. The heartbeat logged "refused" every thirty seconds for ever, the coordinator marked the node stale and stopped handing it to clients, and the process sat there healthy serving nothing until somebody noticed and restarted it. Both halves recover by themselves now: the agent registers again with its key, and the server beside it rereads the credential the agent just wrote.

    A node that goes quiet for ninety seconds is marked stale and withheld from new downloads while existing ones drain. That is a health signal rather than a disconnection — it returns to online on the next heartbeat that lands. Check Admin → Nodes for when each was last heard from.

    When it does not

    SymptomAlmost always

    Two nodes take turns flagging each other's games missing They share a library. They must not.
    The mesh is on, nodes are online, downloads still come from the origin No chunk hashes yet. Check hashed-of-total on each node's page — the sweep may still be working through the library.     Some players download and some cannot NAT. Run mesh-doctor on the affected networks. A symmetric or carrier-grade NAT cannot form this direct-only tunnel; move either peer to a punchable network.

    Overview

    Catalog health, connected clients, scan progress, and a broadcast announcement box that pushes a notification to every account.

    Catalog

    • Games — a worklist of every game, filterable by match status and by what an entry is still missing: no launch executable, no cloud-save rule, no artwork, no achievements, no metadata. Each filter carries a server-wide count, and every row shows the same four things as EXE / SAVE / ART / ACH markers, so a scan down the list says where the holes are without opening anything. Opening one gives a full metadata editor: fields, artwork slots, screenshots, Steam achievement import, and the launch and save rules the desktop client needs.
    • Achievements — the same job across the whole catalog rather than one game at a time. See In bulk.
    • Featured — curates the carousel on the client's Home tab, in order, with a per-slot image override.
    • Launch rules — what the client runs once a game is installed, across the whole catalog rather than one game at a time. Every row lists the executables actually inside that game's folder, with uninstallers and redistributables filtered out and the one whose name matches the title pre-selected, so a rule is picked rather than typed. Defaults to the games with no rule; “Accept N suggestions” fills a whole page at once. Arguments, a working directory and a typed path sit behind Advanced on each row — the typed field is for the case a picker cannot cover, such as an executable an installer creates. Archives list their contents when a row is opened, since a zip has to be read to know what is inside it.
    • Save paths — where each game keeps its saves. See Where the save paths come from.
    • Libraries — the folders on disk that are scanned, and the scan itself. See Scanning. Standalone only — a coordinator has no disk, so since 0.6.4 this tab is not shown on one and the routes behind it are refused. Its libraries are made for its nodes when they enrol and are managed under Nodes; each node scans its own disk from its own page.

    Players

    • Invites — codes, their uses and their expiry.

    • Bug reports — the triage queue. See Reporting a bug.

    Nodes

    A section of its own, with four tabs. It was a tab inside Settings, filed next to the Discord token and the API keys — which put “is my archive being served” in the drawer you open once during setup. A node that quietly stops reporting is a catalog that quietly stops being downloadable, and nothing else on the panel says so. /admin/settings/nodes redirects here.

    Shown on a coordinator and on a standalone server; a node has no panel at all, only its own page.

    • Fleet — every machine, with the numbers that explain it rather than just describe it. The pairing that matters is what a node is offering against what is in its library: a node announcing four hundred of two thousand games is working perfectly and still not serving most of the archive, because the rest are not hashed yet. Either number alone says nothing. Beside them: bytes served over a day, a week and all time, how many players it served, how many transfers are open right now, its agent build, how long since it was last heard from, its addresses, and the library its reports land in.
    • Tunnel map — every connection the coordinator believes is open, drawn. See the tunnel map.
    • Analytics — the share of delivered bytes that never touched this server, which is the number the mesh exists to move; node and origin traffic drawn separately over 7 to 90 days; catalog coverage (games no online node holds, and games exactly one node holds); the busiest nodes and most-pulled games of the week; and what the relay has been asked to carry.
    • Enrolment — generate a code, and the list of outstanding ones with their expiry.

    The tunnel map

    A table of transfers answers “how much”. It does not answer the question an operator actually has about a mesh, which is shape.

    The coordinator sits in the middle, its nodes ring it, and the players pulling from each node fan out beyond. A direct tunnel bows outward and never touches the middle. A relayed one is drawn straight through it — because that is exactly what it does, and a fleet that has quietly fallen back to the relay is a fleet paying the bandwidth bill the mesh was built to avoid. Dashes flow along a tunnel while bytes are moving and stop when they are not, so a stalled transfer looks stalled.

    Click any tunnel for who, what, how fast, how long it has been open, and how many hole punches it took. Filter to what is moving or to what is relayed. Pause the whole thing to read one line without it moving under the pointer. A table underneath carries the same data for anyone who would rather have rows.

    It says what it knows, not more. A direct transfer never crosses the coordinator, so what is drawn is what each node last reported on its heartbeat — up to half a minute old, and the page shows the age of every tunnel's last report rather than implying it is watching the wire. A tunnel appears the moment permission to fetch is issued and leaves five minutes after anything was last heard about it. For the first half-minute a handshake in progress and one that failed look the same from here, which is what the connecting state means.

    Players' addresses are reduced to a network — 203.0.x.x — before they reach the page, because this is a screen people leave open.

    Scanning

    A scan walks each library root, reconciles what is on disk against the catalog, and then asks the metadata providers about anything new. Admin → Catalog → Libraries starts one and shows what it is doing on a standalone server; on a node it is the node's own page. A coordinator has no disk and does not scan — see the roles.

    The scanner was rebuilt in 0.5.3. If you have been living with a scan that ran from boot and never finished, this section is the one to read.

    The three phases, and what their numbers mean

    PhaseThe count is
    Reading Top-level folders inspected, out of how many the root holds. It cannot know how many games that will be until it has looked inside each one.
    Indexing Entries reconciled with the database, out of what reading found.
    Fetching metadata Titles asked about, out of everything still waiting on a provider.

    Counters are cleared when the phase or the library changes. They used to carry over, which is why a run part-way through its second root would sit on the first root's finished tally — a complete-looking number that was not measuring anything.

    Skip, Stop, and the stall warning

    Skip this one abandons whatever is in front of the run — an unreadable folder, a provider that will not answer — and moves on. It aborts the request in flight rather than waiting for it, so it takes effect immediately.

    Stop the scan ends the run at the next checkpoint. What has already been indexed stays indexed; a cancelled scan is a partial scan, and the next one carries on from there.

    If no counter has moved for three quarters of a minute, the panel says so and how long it has been. A working scan and a wedged one look identical from a progress bar; that line is the difference between waiting sensibly and waiting for ever.

    The ceilings

    Every phase carries a deadline, because each of these has caused a run to hang:

    • 90 seconds per title during metadata. A title is not one request — it is a search, a fetch, a cover and up to twelve screenshots, each with its own timeout and retry. Multiplied out, one game could legitimately occupy a run for the better part of an hour.
    • 30 minutes per library during reading. A share that has gone away does not fail, it hangs: every directory read blocks on a mount that will never answer.
    • Twelve screenshots per game. Nobody scrolls to the thirtieth, and each one past that is a download the first scan of a library pays for, per game.

    The reading walk hands the event loop back every two hundred entries, so the server goes on answering requests — including the progress endpoint you are refreshing to find out what is happening — while a large share is being read off a slow disk.

    What enrichment does and does not touch

    Enrichment is a first-time job. Once a provider has written to a game, it is left alone, so a title corrected by hand or artwork chosen deliberately survives the next scan. Clearing a match from the game's page is what puts it back in the queue.

    A game the providers have never heard of is set aside for the rest of the pass rather than re-asked in every batch, and the run says at the end how many are still without metadata so they can be matched by hand.

    A game that vanishes from disk is flagged, never deleted — an unmounted share must not destroy hand-made metadata matches. Remove missing on the catalog page clears the flagged ones out when you actually mean it.

    The database

    SQLite, in DATA_DIR, with plain-SQL migrations applied at boot. There is nothing to administer day to day — but a catalog on a spinning disk is a different proposition from one on an SSD, and 0.5.3 tunes for it.

    A 64 MiB page cache, a memory map, 8 KiB pages on a newly created database, and a write-ahead log that checkpoints a quarter as often. Ten indexes were added for queries that had none: every shelf and library page filters on "not missing" and then sorts, which a single-column index only half satisfies.

    Maintenance

    Statistics and a log checkpoint run hourly by themselves. SQLite only gathers query statistics when asked, so a catalog that grew from fifty games to five thousand is otherwise still being planned as though it were small — and on a disk that charges milliseconds per seek, a plan that scans instead of seeking is the difference between a page load and a wait.

    Admin → Insights → Health → Database has both jobs as buttons:

    • Refresh statistics — cheap, safe at any time. Worth pressing right after importing a large library rather than waiting an hour for the hourly run.
    • Rebuild and compact — rewrites the file with its pages in order and gives back unused space. This is the one that repays real time on a spinning disk, and also the expensive one: it needs room for a second copy of the database on the same disk and holds a write lock for as long as it takes. The panel shows how much there is to reclaim so you can judge whether it is worth it.

    Users and invites

    Registration is invite-only unless an administrator turns on self-registration in Admin → Settings.

    To add someone: Admin → Players → Invites → Create an invite, then send them the copied link. Invites carry a role, a use count and an optional expiry, and can be revoked at any time. After registering they download the Windows client and sign in there — the web surface has nothing else for them.

    Changing a password signs out every other session and revokes every desktop device for that account.

    Working on the catalog

    Picking artwork

    Every image slot — cover, banner, hero, logo/text, icon, and each screenshot — has a Browse gallery button that opens a picker over everything IGDB and SteamGridDB publish for that title. Search by whatever the providers call the game rather than what the folder is called, and narrow by SteamGridDB style (a white or black text wordmark, a capsule with no logo baked in, and so on). The screenshot picker stays open so a set can be assembled in one pass.

    Previews are streamed through the server rather than loaded from the provider CDNs, so a browser never talks to IGDB or SteamGridDB directly. Only the image actually chosen is downloaded and cached.

    Launch and save rules

    These are what turn an archived folder into something playable:

    • A launch rule names the executable relative to the install folder. Leave it blank and the client picks the largest .exe that is not obviously an installer or uninstaller.
    • A save rule says where the game keeps its saves, using placeholders that resolve on each machine: {userprofile}, {appdata}, {localappdata}, {documents}, {savedgames}, {public}, {programdata}, {windir} and {install}. Optional include and exclude globs narrow it further.

    Checksums

    Hashing a game's files is what lets the client verify what it downloaded, and it is opt-in per game because it reads every byte — far too expensive to do automatically across a multi-terabyte archive. Verifying re-hashes what was hashed before and records whether each file still matches: for an archive, a changed file is almost always corruption rather than an edit, and nothing else here would ever notice. Findings land on Health.

    Neither has a control in the panel as of 0.6.1. Both are API calls. If you are turning the mesh on, run the chunk pass instead — it writes the whole-file checksums as it goes, so it does this job too. See computing chunk hashes for all three routes and a worked example.

    Games players already have

    A player with a drive full of games should not have to download a second copy of any of them. Library → Import points the client at a folder, finds every subfolder holding a Windows executable, and matches those names against the catalog — through the same title parser the scanner uses, so a Hollow.Knight.v1.5.78.11.GOG-FitGirl folder still resolves. Each row is confirmed by hand before anything is linked, because a wrong match would attach the wrong cloud saves to the wrong game.

    Linking copies and moves nothing; the files stay where they are. Unlinking is therefore a separate action from uninstalling, and only the latter deletes.

    Cloud saves

    The client hashes the save folder, zips it, and uploads it as an immutable version. Ten versions are kept per slot, so a bad sync is always recoverable.

    Conflicts are detected rather than guessed at. The client remembers the digest it last synced; when the cloud has moved on from that digest and the local copy has changed too, both sides hold edits and the client asks instead of picking a winner. Launching a game pulls a newer cloud save first, but deliberately does not resolve a conflict — starting a game is the wrong moment to make someone choose which save to destroy.

    Restoring moves the existing save folder aside rather than deleting it, so the previous state stays on disk even if the archive turns out to be wrong.

    Automatic syncing

    The setting has said "pull before launching and push after quitting" since the client was written, and only the pull was ever implemented — so a player who trusted it had a cloud copy frozen at whenever they last pressed Upload, and a fresh install would then restore that over their real progress. Uploading now happens too.

    Settings → Cloud saves in the client. The master switch turns automatic syncing on; underneath it, three controls decide when:

    • Upload when a game closes. On by default. There is a short pause first — a game writes its save on the way out and the process is gone before the disk has finished, and packing the instant the process disappears uploads the save from before the session.
    • Catch up on sign-in. On by default. A crash, a power cut or closing the launcher mid-game all end a session with nothing uploaded; this is the sweep that notices, and it is why "automatic" can be trusted at all.
    • Back up while playing. Off by default, five minutes to an hour. A long session that ends in a crash otherwise loses everything since it started. It costs an upload per interval, and for a game that holds its save file open it can capture a half-written one — hence off unless asked for.

    A conflict is never resolved automatically. That stays a decision on the game's page.

    Where the save paths come from

    Finding where a game saves by hand means installing it, playing it, making a save and going looking — for every title. Admin → Catalog → Save paths matches the catalog against Ludusavi's manifest, a machine-readable digest of PCGamingWiki's save-path data covering close to twenty thousand games, and proposes the rules instead.

    Nothing is written without a tick, and the manifest's own title is shown beside the archive's on every row, because a title match is occasionally confident and wrong — and these paths are where the client will later read and write a player's saves. Titles that already have a rule are hidden by default.

    The index refreshes itself daily, decided from its own age rather than run on a timer, so a server restarted every evening still refreshes once a day and one left up for months does not drift. Refresh index forces it.

    Achievements without cloud saves

    A game with unlock rules and no save rule is not a game whose save location is unknown. An unlock rule reads a file the game wrote into its own save folder — a Goldberg achievements.json, an emulator's progress log, a stats file next to the slots. So the location has already been written down, in a column that syncs nothing.

    The same page now derives them. Rules pointing into one folder fold into a single proposal; a nested path folds into its parent; two genuinely separate layouts — a retail install and an emulator — are offered as a choice rather than one picked at random. Nothing is written without a tick, and a game that has gained a rule since the page loaded is left alone.

    Health calls this out separately from the plain "no save rule" count, because those players lose their unlocks along with their saves the first time they change machine — and a save can be copied back by hand, while an unlock cannot.

    Achievements

    Games here have no achievement runtime of their own, so definitions are imported and unlocks are reported by the client.

    Import a set from Admin → Catalog → Games → (a game) → Achievements with a Steam app id. This reads Steam's published achievement schema — no player data is requested and no Steam account is linked — which is what makes it usable for a DRM-free copy of a game that also ships there. Global unlock rates come along with it and set each achievement's point value.

    In bulk

    One game at a time is right for a correction and hopeless as a way to cover a catalog of several hundred, so Admin → Catalog → Achievements does the same job across as many games as you select.

    It starts on the games that have none. Tick the ones you want — or all of them — and it works through the list, finding each on Steam, importing its published list and writing the unlock rules, a few games at a time so you can watch it go and stop it. Every game gets a line saying what happened, and the ones that could not be done automatically sort to the top: a title Steam places ambiguously, one it has never heard of, and one whose store entry has no achievements are all ordinary across a real catalog, and each is a note rather than a failed run. Games that already have achievements are left alone unless you say otherwise.

    For the games Steam cannot help with — a fan translation, an itch-only release, a version whose store entry predates its achievements — the same page takes a pasted list. One per line: the name, then optionally a description, a point value and a key, separated by tabs, commas or pipes, so a column copied out of a spreadsheet or a wiki table works as it is. A missing key is derived from the name and stays stable, so a corrected list can simply be pasted again.

    Achievements that unlock themselves

    Definitions have always been importable; a rule is what says when one is earned. It names a file the game itself writes and what to find in it — a JSON path, an INI key, or a regular expression over text — tested for presence, truthiness, equality, or a threshold.

    The client reads those files when a session ends and reports only the resulting keys; the files never leave the machine. A reported key with no rule behind it is ignored, so reporting is not a way of simply asking for an achievement, and unlocking is idempotent, so re-reading the same save changes nothing.

    One achievement often needs a rule per save layout it might turn up in — Goldberg, a retail install, an emulator — all naming the same key and told apart only by a long path. Rules carry operator tags for exactly that, on the rule rather than on the achievement, because the rule is the only thing that distinguishes them.

    Because the client is the only thing that can observe progress, unlocks are self-reported and therefore not cheat-proof. The server keeps them idempotent and well-formed; it does not adjudicate them.

    Game requests

    Players ask for what is not there, and the archive keeps a queue of it.

    The client's Requests tab is where players ask and vote: a tally of what is open, on the way and already added, a search, filters by state, and the queue ranked by votes. Two people asking for the same game strengthen one row rather than producing two the operator has to reconcile — titles are matched on a normalised key, so Half-Life 2: Episode One and half life 2 episode one collide, while Halo and Halo Wars stay apart. The asker's vote is counted automatically, and anyone else can back a row or take their backing away.

    Above the queue sit discovery shelves: what is being played elsewhere, what is anticipated, what is newly out and what is best reviewed, from IGDB. Each card is checked against this archive first, so its button reads In the archive, Backed, Back it or Request — one click, no typing. It needs IGDB credentials; without them the shelves simply do not appear and the rest of the page works as normal. The lists are cached for an hour, since they are the same for every player and IGDB's rate limit is shared with scanning and matching.

    Cards are clickable. A title the archive already has opens the game — the same panel the Store opens, with its screenshots, its size and its Install button. One it does not have opens what the provider told us about it: the cover, the full blurb, the year, the score, and the button that asks for it. That is deliberately not the game drawer, which is built around a game that exists here; reusing it would have meant a page of dead Install and Play buttons.

    Admin → Players → Game requests is the other side of it: the queue ranked by votes, with four states — pending, coming soon, added, denied — a note players will see, and a field linking a fulfilled request to the catalog entry that satisfied it. Who asked is shown here and nowhere else; a wish list should not become a public record of who wants what.

    The client's Home tab draws the result: Coming soon for what has been promised, Most requested for what is still wanted, and Recently granted for requests that made it in — with an Open button straight to the game. A denied title reopens as pending if somebody else asks for it, because the second asker never saw that decision.

    Social, news and profiles

    The feed

    Screenshots, clips and text, with comments and reactions. Friends have live presence and a shared activity feed. Clips play where they sit with the browser's own controls, and expand into the media viewer from a corner button.

Players cannot author one — the post route derives its kind from what was attached, so asking for kind: announcement in a request body is ignored rather than trusted.

    Profiles

    A display name, a bio, an avatar, a banner, an accent colour, a country, and who may see any of it — everyone on the server, friends only, or nobody. A private profile still resolves so the "add friend" screen has a name to show, but every statistic is withheld rather than faked.

    0.5.3 adds room for a profile to be somebody's rather than a name and an avatar:

    • Pronouns. Free text rather than a list of options, because no fixed list is complete and one that is not gets it wrong for exactly the people it matters most to. Shown beside the name, and visible even on a private profile — withholding it would make a locked-down profile misgender its owner to everyone who visits.
    • A status line, distinct from the bio: what, right now.
    • Banner framing. A banner is a wide crop of a much taller picture, and left at dead centre it beheads people. A slider chooses which band survives.
    • Up to five labelled links. Capped, because an uncapped list becomes a link farm; labelled, because an unlabelled URL on somebody's profile is one nobody clicks. Only http(s) is accepted, checked on both sides.
    • One pinned game, as distinct from "most played" — which is what the section calling itself Favorite games actually was, and is now labelled as.

    Showing a Discord handle

    A linked player's handle is private by default. The toggle lives on their account page, and re-linking — which happens on every Discord sign-in — does not turn it back on.

    Turning it on used to change the friends rail and nothing else, including the profile page it is named after. Every path that builds a profile summary now resolves the handle the same way, so the answer is the same everywhere.

    Messages

    The Messages tab in the client. Text, images and video, between friends or in a group of up to 32.

    Using it

    • Friends only. An archive with open messaging is one where any account can send anything to any other, which is the shape every spam and harassment problem takes. Adding somebody is already the gesture that says "I want to hear from you".
    • Picking more than one person makes a group. Whoever starts it owns it and can rename it and add people; anyone can leave. A member who leaves stays in the record with a departure date, so the messages they sent still have a name against them.
    • Attachments are ordinary uploads that count against the same media quota as screenshots and clips, and open in the media viewer.
    • Withdrawing a message clears its text rather than hiding the row, so every client agrees it is gone. It does not reach into the screen of somebody who has already read it, and nothing could.
    • Enter sends, shift+enter breaks the line. The composer is pinned to the bottom of the window and the conversation list scrolls beside it, so neither moves with however much history is above them.

    These are not end-to-end encrypted, and the operator can read them. 0.5.3 shipped an encrypted version and 0.5.3 took it back out: the cost was out of proportion to what this is. An operator already holds every save file, every screenshot and every password hash on the server, so wrapping message bodies protected nothing that was not already readable — while adding a failure mode that was very real, where a device with no key wrap for a conversation could not read a word of it and nothing could recover one.

    Access control is the security model, and it is the half that was always doing the work: friends only, membership checked on every read and write, and an attachment that has to belong to whoever is attaching it. Treat a conversation as private from other players and visible to whoever runs the server — which is the same understanding that already applies to everything else stored here.

    The client is where players spend all their time.

    Adding a game to your library applies immediately and only to the card you clicked, so a run down the store adding a dozen titles is a dozen clicks rather than a dozen round trips waited out one at a time.

    Installing, launching and playtime tracking are handled in Rust: the client extracts the archive, resolves the executable, watches the game process and banks playtime as it goes, so a crash mid-session still keeps most of it.

    Presence, friend activity, notifications and new messages arrive over a WebSocket that reconnects with backoff. Everything it carries is also readable over REST, so a dropped socket costs freshness, never correctness.

    Stopping a game

    While a game runs, the Play button used to become a greyed-out "Running" — true, and no help at all to somebody whose game has hung behind a fullscreen window they cannot get back to. The only way out was Task Manager.

    The game's page, the right-click menu and the chip in the title bar all offer Stop. The process is asked to close first, so a game that handles the request gets to save, and killed five seconds later if it does not answer. Playtime is recorded exactly as for a normal exit, because it was time played.

    Library layouts

    LayoutFor
    GridBrowsing by artwork
    ListFinding a title you already know — four or five times as many rows on screen
    DetailedDeciding what to play: cover, blurb, genres and every stat spelled out

    Switched from the toolbar rather than from Settings, because which one is right changes with what you are doing. The choice lives in the client's settings file, so it survives a restart. Game pages show a title's logo artwork in place of its name wherever the archive has one; Settings → Appearance turns that off for anyone who would rather read the title.

    Groups

    A player's own shelves, private to their account. Right-click any game and choose Add to group… to file it — or make a group in the same dialog and file it there in one step. The Library tab then shows a chip per group beside the search box.

    Groups are per-account rather than server-wide: an operator already has genres and the featured rail to shape the catalog, and a shared group would need its own permissions model to answer "who may rename this". Nothing is copied or moved, and deleting a group leaves every game in it alone.

    The media viewer

    Screenshots used to open into the 440-pixel dialog the app uses for confirmation prompts, so a 1080p capture rendered at about a fifth of its size with text buttons underneath for Previous and Next. Trailers left the app for a browser.

    Both now open the same full-viewport viewer: arrow keys between items, a filmstrip, a counter, and a fit/full-size toggle for reading small text in a capture. Trailers play inline through YouTube's privacy-preserving embed host with related videos from other channels switched off, and "Open on YouTube" is still there. Clips in the feed and attachments in a conversation play with the browser's own controls — scrubbing, volume, playback rate, picture-in-picture.

    Working offline

    The archive runs on your own hardware, so it is down sometimes — a reboot, a moved cable, a laptop on a train. Any of those used to take the whole client with it: the sign-in check failed, the app fell back to the login screen, and the login screen could not reach the server either.

    What works with the server unreachable:

    • You stay signed in. An unreachable server is not the same answer as a revoked device, and is no longer treated as one.
    • Installed games launch, and playtime is recorded when the server comes back.
    • The library lists what is on this disk, from the install records themselves — so changing the sort does not empty the page.
    • Pages you have already visited render from the last answer the server gave.
    • Artwork falls back to the initials placeholder rather than a broken-image icon. Covers are fetched from the server, so offline the library is a grid of titles rather than posters — plainer, and a great deal better than no app at all.

    A banner says what still works rather than only that something is wrong. Anything that writes fails with "this needs a connection" instead of a TLS error. Messages are the one feature that genuinely cannot work offline, and the tab says so.

    Downloads

    Pressing Install asks where the game should go rather than silently using a default. Every configured drive is listed with what is free, what would be left after, and a plain refusal when the game will not fit — a download that dies at 90% for want of disk is the worst way to find that out. Add more locations under Settings → Storage.

    A browser download of a 60 GB folder is a single connection that has to survive from start to finish; if it drops at 90%, it starts over. The desktop client exists to remove that failure mode.

    • Fetches a manifest of every file in a game with a short-lived signed token.
    • Multiple connections per file (files ≥ 32 MB are split into four ranges) and several files in parallel.
    • Resumes after a disconnect, a crash or a reboot. Progress is journalled to a .gbpart sidecar next to each file, so a transfer picks up at the exact byte it stopped.
    • Retries with backoff — a flaky tunnel recovers on its own instead of failing the download.
    • Verifies SHA-256 when the server has a checksum for a file. See Checksums.
    • Signs in with a device token in the Windows Credential Manager, never a password on disk. Each device is listed and revocable from Settings.

    Cancelling asks what to do with the bytes already on disk. Stopping a 250 GB install 100 GB in leaves 100 GB somewhere, and both answers are legitimate — a transfer stopped to be resumed later wants its files, one being abandoned wants the space back. Keeping them is the default; removing them deletes exactly the paths that download wrote and nothing else in the folder.

    Web downloads still work for everything: archive games stream with byte-range resume support, and folder games are packaged into a ZIP on the fly.

    Right-click menus

    Right-clicking a game anywhere in the client — Home, Library or Store — opens a menu with everything that applies to it: play, stop, install, add to library, favourite, open the install folder, unlink, uninstall, plus any custom buttons placed there. Text fields keep the native menu, so copy and paste still work.

    Keeping the client up to date

    Upload a new installer under Admin → Settings and bump the client version beside it. Clients older than that version show a banner offering to update, and hand off to the installer when the user accepts — nothing is replaced behind their back. Declining is remembered per version, so saying no to 0.5.2 stays no while 0.5.3 asks again. Nothing is offered unless an installer has actually been uploaded.

    Reporting a bug

    Report a problem sits in the client's sidebar, reachable from wherever something went wrong rather than on a page somebody has to go and find. The report carries the client version, the platform, the game if one was running, and the last few errors the app logged — none of which a reporter should have to know, and all of which an operator would otherwise have to go back and ask for.

    Admin → Players → Bug reports is the queue: filter by state, read what the app logged just before, and answer. Whatever you set, and anything you write back, reaches the reporter as a notification, and they can see where each of their reports got to under Settings.

    That last part is the point rather than a nicety. Somebody who reports a problem and never learns whether it was read, fixed, or was never a bug has no reason to report the next one, and an archive tested by the people using it depends on them doing so. Unanswered reports show up on the health page for the same reason.

    Discord

    Entirely optional — with none of it configured, GameBlade behaves exactly as it did before. Admin → Settings → Discord has two independent halves.

    Sign in with Discord

    Needs a Discord application's client ID and secret. Players can then link from their account page and use it to sign in. Linking never creates an account: this server is invite-only, so an unlinked Discord is told to sign in normally once and link. The redirect URI registered on the application must exactly match <your server>/api/auth/discord/callback.

    With a guild ID set, linking also checks membership of your Discord, and the bot adds them to it using the guilds.join scope they granted — being told to go and join is a step people do not take. If that fails, they get your invite link instead. Require players to be in the server refuses the link outright when neither works.

    Starting the bot

    A token lets this server post; it does not make the bot online. Being in the member list, answering a slash command and reacting to a button all need a live gateway connection, and Start the bot is what opens one. The switch is remembered, so the bot comes back by itself after a restart, and it reconnects on its own if Discord drops it. A wrong token stops it outright and says so rather than retrying for ever.

    Intents are assembled per feature, so a server using none of them keeps exactly the bot it had: Guild Members is added only when an auto-role is set, and Message Reactions only when reaction roles are switched on. Both are read at connect time, so changing either reconnects rather than leaving a live socket listening for events it never asked for. Guild Members is privileged and has to be enabled in the developer portal — the panel says so, because that is the step that otherwise fails as "the bot will not connect".

    How it appears sets the coloured dot (online, idle, do not disturb, invisible) and the line under the name: Playing, Streaming, Listening to, Watching, Custom or Competing in, plus the text. A change is pushed over the open connection, so it takes effect immediately rather than bouncing the bot offline and back.

    Posting, and tagging people in a post

    Post something goes to whichever channel you pick — the channel and role boxes are real pickers once the bot can see your server, and fall back to pasting an ID when it cannot. An attached image is sent as a genuine Discord attachment rather than as a link, so it works whether or not this server is reachable from the internet.

    The composer has three pickers — people, roles, channels — that insert a real mention at the cursor. Typing a snowflake by hand works and nobody does it: it has to be copied out of Discord with developer mode on, and a mistyped digit produces a post that looks fine and pings nobody.

    Discord never notifies for a mention inside an embed. A role pill in an embed description renders correctly and reaches nobody — that is Discord's rule, not a formatting mistake, and there is no flag that changes it.

    The only fix is to repeat the mentions in the message content that carries the embed, which the composer offers as Notify the people tagged and explains rather than leaving to be discovered. Untick it for a post that should mention somebody without pinging them.

    Every outgoing message carries an explicit permission list naming exactly the ids the text contains. Omitting that field would tell Discord to notify anything that looks like a mention, which is how a game summary containing the word @everyone would ping a whole server. @everyone itself is opt-in on top of that, with its own tick, because it is the one mention nobody should send by accident.

    The member picker is filled from accounts linked here, topped up from your guild when the privileged Members intent happens to be enabled — so it works either way rather than requiring a trip to the developer portal.

    Auto-role and reaction roles

    An auto-role is handed to everyone who joins. A reaction role binds one emoji on one message to one role, keyed on the pair since a message normally carries several choices; the emoji is stored in the shape the gateway reports it, so matching is a string equality rather than a guess. Adding a binding also puts the emoji on the message, and says so when it could not.

    Both failure paths log the real cause, which is almost always the bot's own role sitting below the one it is trying to grant.

    Support tickets

    They work the way Ticket Tool does. Post a panel into a channel and it carries a button; pressing it asks what the problem is, then opens a private channel that only that person, your staff role and the bot can see. Closing it asks once, deletes the channel and keeps the record in the panel — a Discord that accumulates two hundred dead #ticket-0042 channels is worse than no ticket system at all, which is why the record lives here rather than there. One open ticket per person. The bot needs Manage Channels.

    Without a staff role every ticket is private to the person who opened it, which is almost certainly not what you want — the picker says so.

    /profile

    Anyone who has linked their account can run /profile in your server and the bot answers with their GameBlade profile: their avatar, how many games they have, hours played, achievements, friends, when they joined and what they are playing right now. The avatar travels as an attachment rather than a link, because the media route needs authentication and opening it to the world to save a round trip is not a trade worth making. Someone who has not linked is told how to.

    The command is registered against your server rather than globally, so it appears the moment the bot connects instead of up to an hour later.

    Configuration and testing

    The bot needs a token, a channel and this server's public address. The address is for cover art: Discord fetches images itself, so a relative path would resolve against discord.com. Paste the bare token from the Bot tab; a token pasted as Bot <token> is accepted too.

    Test walks every step between that token and a message arriving — the token itself, whether the bot was ever invited to your server, whether it can see the channel you named, and whether it may post there — and reports each separately, because those are the things that actually go wrong and they all look identical from outside. A passing run leaves a test message in the channel.

    It can post whatever you type, announce newly added games every fifteen minutes, and announce requests as they are granted. Turning announcements on starts from that moment rather than posting everything already in the catalog, and only games whose metadata matched are announced — an unmatched entry is a folder name with no cover and no blurb.

    Discord publishes no friends list to third-party applications. There is no scope for it and no endpoint. "Friends from Discord" therefore means other players here who are in the same server as you, which is the closest the platform allows — and since linking pushes everyone into that one server, very nearly the same set.

    Theming and the landing page

    Theming

    Ten presets — eight dark (Midnight, Slate, Carbon, Nebula, Aurora, Ember, Moss, Oceanic) and two genuine light ones (Daylight, Parchment) — plus an optional accent colour that replaces the preset's own. Only the mid step is picked; the lighter and darker steps are derived from it, so hover, focus and gradient states keep working without asking anyone to choose four related colours by hand.

    A theme is a complete surface ramp rather than one hue: brightening only the accent on a near-black chrome produces something that reads as broken. The tokens are resolved server-side and applied by both the web app and the desktop client, so a server's look is one setting rather than two that drift.

    Players can disagree. The client's Settings → Appearance offers the same ten themes and the same accent picker, stored in that machine's settings file. Picking one overrides the server's for that PC only; Follow the server hands it back. An operator chooses the look of their archive, and nobody has their desktop restyled the next time that choice changes.

    Publishing the Windows client

    Admin → Settings takes the installer itself: pick a .exe (or .msi, .msix, .appinstaller, .zip) up to 1 GB and it is stored on the server and served from the landing page's download button, with its size shown alongside the version. One build is kept at a time — uploading again replaces it.

    CLIENT_DOWNLOAD_URL and the URL field beside the upload still work and are used whenever no installer has been uploaded, so an existing deployment keeps pointing wherever it already did.

    Bandwidth, health and backups

    Bandwidth

    Two limits, both off by default (0 means no limit), under Admin → Settings:

    • A download speed cap in KB/s, applied per stream. A client opening several connections gets that much on each, which is the honest way to describe it.
    • A monthly allowance per account, in MB, resetting on the 1st. Override it for one account on the Users page — an explicit override binds even for an administrator, while the server-wide default deliberately does not apply to them, so a default can never lock the operator out of their own downloads.

    An account over its allowance is refused with 429 before any bytes are sent, and a single transfer that would cross the line is cut off mid-stream — usage is only recorded when a stream closes, so a start-only check would let one oversized download sail straight past.

    Health

    Admin → Insights → Health answers "is anything wrong", which analytics does not: disks running out, games that have gone from disk, entries with no launch or save rule, games tracking achievements they cannot sync, files whose contents no longer match their recorded checksum, accounts that have hit their limit, unanswered bug reports, when the library was last scanned, and node coverage. Every finding links to where it is fixed. It is all derived from rows already being written, so there is nothing to keep in step by hand.

    Backups

    An archive holds the database, every player's cloud saves, uploaded media and the published installer — the things that exist nowhere else. The game library is deliberately left out: it is enormous, you already have it, and a scan rebuilds the catalog from it. Cached artwork is out too by default, being both the largest part and the one part that can be fetched again.

    The database is copied through SQLite's own backup API rather than by copying the file. Under WAL the file on disk is not a complete database on its own, and copying it during a scan produces an archive that restores to a corrupt state.

    The schedule is three settings on Admin → Insights → Health, not environment variables: how many archives to keep (7), how many hours between runs (24, and 0 turns automatic runs off), and whether to include cached artwork (off). They are written into DATA_DIR/backups, which is itself left out of them.

    To restore: stop the server, unzip the archive over an empty DATA_DIR, start it again. On a coordinator that is the whole restore, since no game files ever lived there; on a standalone server the library is separate and was never in the archive to begin with.

    The external API

    A versioned, key-authenticated API at /api/v1 for driving the server from elsewhere — provisioning accounts from a billing system, handing out invites, reading stats. Keys carry explicit scopes, and users:admin is separate from users:write so a provisioning key cannot mint itself an administrator.

    Full reference, including a worked provisioning example: docs/API.md.

    Cutting a release

    Releases come from CI, and only from CI. The PowerShell build scripts are gone. There is no longer a step that depends on somebody having a Windows machine, the right toolchain on it, and the discipline to run the same command every time — which is the arrangement that lets a release ship with one manifest still on the previous version.

    Two steps, and the second one is a tag:

    # 1. Stamp the version across every manifest that carries one.
node .github/scripts/set-version.mjs 0.6.2
git commit -am 'Release 0.6.2'

# 2. Tag it. Everything else happens on GitHub.
git tag v0.6.2
git push origin main --tags

    The Publish workflow then, in order:

    1. Checks every manifest agrees with the tag and stops if not. Ten files carry the version and five different tools read them; a release where they disagree is not a broken build but an installer that reports the wrong version to the update check, which is worse, because it ships.
    2. Builds and pushes the four images — standalone, coordinator, node, plus the legacy relay — from one Dockerfile, tagged latest, the version, and the major.minor.
    3. Builds the Windows installers on a Windows runner.
    4. Publishes the release with the .exe and .msi attached and notes naming the images.

    set-version.mjs --check is the same script CI runs, so a disagreement can be found before pushing rather than after.

    Publish can also be run from the Actions tab with a version typed in, for a release from a branch that cannot push tags. build_client forces the Windows job outside a release, for checking a client change without cutting one; a release always builds it, because there is no other way to get one now.

    Ordinary pushes to main refresh the latest images and build nothing for Windows unless the client's own code changed. Windows minutes bill at twice the Linux rate and a release build with full link-time optimisation is long, so it is spent on the pushes that could plausibly ship and not on the ones that touched the admin panel.

    Security notes

    • Passwords are hashed with Argon2id using OWASP's low-memory profile.
    • Session tokens are opaque and stored only as SHA-256 hashes.
    • State-changing requests from the browser require a CSRF header; bearer-token requests from the desktop carry no ambient authority and are exempt.
    • Every download path is re-resolved against its library root and symlink-checked before any bytes are served, so a crafted path cannot escape the mount.
    • The container runs as a non-root user and the library is mounted read-only.
    • Archive entries are attacker-controlled, so both the game installer and the save restorer rebuild every path from its normal components and reject anything containing .. or a root — the zip-slip escape.
    • Uploaded saves are verified against the digest the client declared before the version is accepted, so a truncated transfer never becomes the copy others pull.
    • Profile visibility is applied when a summary is built, per viewer, so a friends-only profile never leaks its current game to a stranger.
    • Messages are stored as text the server can read; membership is checked on every read and write, and messaging is friends-only. What that does and does not mean is set out under Messages.
    • Outgoing Discord messages carry an explicit mention permission list, so text the server did not write cannot cause a notification.
    • Profile links are checked for an http(s) scheme on both sides, since the value lands in an href on a page other people open.
